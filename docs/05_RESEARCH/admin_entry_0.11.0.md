## Q1. Что ВК документирует про открытие новой вкладки из окна Mini App

**ПОДТВЕРЖДЕНО.** На платформе `vk.com` (десктопный веб) мини-приложение —
это обычная веб-страница, загруженная в HTML-элемент `iframe` внутри
страницы ВКонтакте. Наша клиентская часть — обычный HTML-документ,
ограничений на стандартные элементы страницы в документации и правилах
размещения нет.
Источник: https://dev.vk.com/ru/mini-apps/development/iframe-webview
(таблица платформ: vk.com — iframe); уже зафиксировано у нас как
факт N1 в `docs/02_SYSTEM_SPECS/00_core_nat_vk_facts.md`.

**НЕ ПРОВЕРЕНО.** Какие именно атрибуты (в частности `sandbox` и его
флаги `allow-popups`, `allow-same-origin`, `allow-scripts`) стоят на
этом iframe — в документации ВК не описано. В наших документах такого
факта тоже нет. Косвенно это покажет проба: `window.opener` и
видимость хранилища из новой вкладки.

**ПОДТВЕРЖДЕНО.** В VK Bridge метода `VKWebAppOpenLink` нет: его страница
в документации отдаёт 404, а в `RequestPropsMap` официального пакета
`@vkontakte/vk-bridge` такого события отсутствует (проверено в типах
установленной версии 2.15.12 —
`frontend/node_modules/@vkontakte/vk-bridge/dist/types/src/types/data.d.ts`).
Ближайший по названию метод — `VKWebAppOpenApp` — открывает другое
мини-приложение по `app_id`, а не произвольную ссылку. Метода
«открыть внешнюю ссылку» в VK Bridge на веб-платформе нет вообще —
в полном списке событий «Обзор» такого метода нет.
Источники: https://dev.vk.com/ru/bridge/overview (полный список событий);
типы пакета `@vkontakte/vk-bridge@2.15.12` (`OpenAppOptions`, см. выше);
факт V15 в `docs/02_SYSTEM_SPECS/02_bot_vk_facts.md`.

**ПОДТВЕРЖДЕНО.** Обычные браузерные способы — `window.open(url, '_blank')`
и `<a href="…" target="_blank">` — открывают новую вкладку штатными
средствами браузера и модерации не требуют (факт V15). Эксперимент E1
(02.10.2026, `docs/03_ROADMAP/01_map.md`) живой проверкой подтвердил:
новая вкладка с нашим адресом из окна ВК открывается и «свободна от
ограничений ВК» (её ширина не ограничена рамкой приложения).

**НЕ ПРОВЕРЕНО (проверяет проба, кнопка «б»).** Разрешит ли браузер
`window.open`, вызванный не сразу по щелчку, а после `await` запроса к
серверу. По общему устройству браузеров всплывающие окна пускаются
только в окне «пользовательской активации» — как она ведёт себя после
ожидания сети внутри iframe ВК, ни ВК, ни мы не проверяли. Именно поэтому
в пробе две кнопки: «сразу» и «после запроса».

**ПОДТВЕРЖДЕНО (по стандарту URI, проверит и проба).** Фрагмент адреса
(всё после `#`) не отправляется на сервер в HTTP-запросе и не уходит в
заголовке `Referer`. Поэтому служебную метку допустимо передавать только
во фрагменте `/admin#t=…`, а не в query `?t=…` — query попадает в логи
Caddy и в историю браузера.

## Q2. Вход через VK ID на нашей собственной странице

**ПОДТВЕРЖДЕНО.** Что нужно зарегистрировать: приложение в кабинете
сервиса авторизации VK ID (`id.vk.ru/about/business/go`), платформа
«Web». При создании заполняются «Базовый домен» (на нём работает
авторизация) и «Доверенный redirect URL» (куда вернётся браузер после
входа и куда придёт авторизационный код; домен должен в точности
совпадать с базовым, адрес — без якоря). Приложению выдаются `client_id`,
«защищённый ключ» и «сервисный ключ доступа».
Источник: https://id.vk.com/about/business/go/docs/ru/vkid/latest/vk-id/connection/create-application

**ПОДТВЕРЖДЕНО — важная оговорка про «без модерации».** Формальной
модерации приложения в документации VK ID нет: после создания приложение
по умолчанию «включено и видно всем», базовые доступы работают сразу,
списка причин блокировки за «непройденную модерацию» нет (блокируют за
нарушение оферты, оформление кнопки не по правилам и работу на доменах
не из настроек). НО вход в кабинет сервиса авторизации возможен только
через **VK Бизнес ID**, а профиль бизнеса нужно подтвердить — иначе
через 60 дней после создания первого приложения оно будет заблокировано
(для аккаунтов, зарегистрированных до 15.12.2025, — с 01.03.2026). Без
подтверждения можно создать не больше 3 приложений и нет полного
доступа к настройкам и ключам. То есть «модерации приложения» нет, но
обязательная проверка данных бизнес-профиля есть — по тяжести для
Project Owner это сопоставимо или тяжелее модерации.
Источники: https://id.vk.com/about/business/go/docs/ru/vkid/latest/vk-id/connection/create-application,
https://id.vk.com/about/business/go/docs/ru/vkid/latest/vk-id/connection/verification

**НЕ ПРОВЕРЕНО.** Требует ли VK Бизнес ID статуса ИП/юрлица или
подтверждается физлицом — в прочитанных страницах не написано; это
нужно смотреть в самом `bid.vk.com` руками.

**ПОДТВЕРЖДЕНО.** Scopes: минимальный набор по умолчанию —
`vkid.personal_info` (имя, фамилия, фото, пол, дата рождения), он же
выдаётся, если `scope` не передавать вовсе. `email` — базовый доступ по
желанию; `phone` — расширенный, после подтверждения профиля бизнеса;
`friends`, `video`, `photos` и другие — «в исключительных случаях»
через devsupport@corp.vk.com. Для входа в панель нам нужен только
идентификатор пользователя — хватает набора по умолчанию, запрашивать
ничего не нужно.
Источник: https://id.vk.com/about/business/go/docs/ru/vkid/latest/vk-id/connection/create-application
(раздел «Настройка доступов»).

**ПОДТВЕРЖДЕНО / частично НЕ ПРОВЕРЕНО.** `POST https://id.vk.ru/oauth2/user_info`
возвращает `user.user_id` — «идентификатор пользователя»; в ID token то же
значение лежит в поле `sub`. Совпадает ли этот идентификатор с нашим
`vk_user_id` из launch params — документация прямо не заявляет:
**НЕ ПРОВЕРЕНО**, проверяется одной живой авторизацией (сравнить
`user_id` из user_info с `vk_user_id` в наших `players`). Отдельная
осторожность: через VK ID можно войти аккаунтом Одноклассников или Mail —
у такого входа `user_id` может не быть vk_user_id ВКонтакте вовсе; для
нас это безобидно — чужой идентификатор просто не пройдёт проверку прав.
Источники: https://id.vk.com/about/business/go/docs/ru/vkid/latest/vk-id/connection/api-description
(раздел «Получение немаскированных данных»),
https://id.vk.ru/about/business/go/docs/ru/vkid/latest/vk-id/connection/tokens/id-token

**ПОДТВЕРЖДЕНО.** При интеграции через API обязателен PKCE
(`code_challenge`/`code_verifier`); обмен кода на токены возможен на
бэкенде (рекомендовано, «конфиденциальное» приложение с привязкой к IP
сервера) или на фронтенде («публичное» приложение).
Источник: https://id.vk.com/about/business/go/docs/ru/vkid/latest/vk-id/connection/api-description

## Q3. Как устроена текущая сессия и почему Bearer нельзя в URL

**ПОДТВЕРЖДЕНО (наш код).** Сейчас вход работает так:
`POST /api/v1/auth/vk` принимает сырую строку launch params, проверяет
подпись HMAC-SHA256 ключом `VK_APP_SECRET` и свежесть `vk_ts` в окне
`vk_ts_freshness_window_minutes` = 30 минут (`configs/00_core.yaml`,
схема 1–120). По `vk_user_id` создаётся или находится игрок, после чего
выдаётся Bearer JWT (HS256, `sub` = `player.id`, подписан
`JWT_SECRET_KEY`), срок жизни `jwt_ttl_minutes` = 60 минут (схема
5–1440). Дальше токен идёт в заголовке `Authorization: Bearer …` каждого
запроса; `get_current_player` декодирует его и каждый раз читает строку
`Player` из базы; `require_admin` дополнительно сверяет `vk_user_id` со
списком `ADMIN_VK_USER_IDS` (переменная окружения, читается на каждый
вызов). На клиенте токен живёт только в памяти React (`useAuth.ts`),
сознательно не сохраняется в `localStorage` — Mini App при каждом
запуске получает новые launch params и новый JWT.
Источники: `backend/src/modules/_00_core/router.py` (эндпоинт
`/auth/vk`), `backend/src/core/security/vk_signature.py`,
`backend/src/core/security/jwt.py`,
`backend/src/core/security/dependencies.py`,
`backend/src/core/admin/security.py`, `configs/00_core.yaml`,
`frontend/src/modules/00_core/hooks/useAuth.ts`.

**ПОДТВЕРЖДЕНО (наш деплой).** Backend работает одним воркером
(`docker-compose.prod.yml`: «backend (single worker)») — значит,
хранилище одноразовых меток можно держать в памяти процесса.

**Обоснование (наша инженерная логика, не факт ВК).** Почему готовый
Bearer Mini App нельзя вставлять в URL новой вкладки:
(1) query-параметры попадают в access-лог Caddy и любых промежуточных
прокси, в историю браузера и в `Referer` при переходах со страницы;
(2) адрес с токеном можно случайно скопировать и переслать — кто угодно
получит 60 минут админского доступа;
(3) даже во фрагменте постоянный JWT живёт слишком долго для «ключа,
который летит по ссылке». Поэтому в URL допустима только короткая
одноразовая метка, которую страница тут же меняет на сеанс, а сам сеанс
держится не в адресе.

## Q4. Рекомендуемая конструкция одноразовой ссылки

Это проектная рекомендация Lead Developer, опирающаяся на факты выше и
на наш код. Числа — предложение, окончательные значения уйдут в
`configs` по инварианту Config-Safe.

### Поток входа

1. В «Штабе» администратор жмёт кнопку панели. Mini App вызывает
   `POST /api/v1/admin/panel-link` (обычный Bearer + `require_admin`).
   Сервер генерирует криптостойкую случайную метку (не менее 128 бит,
   `secrets.token_urlsafe`), записывает в хранилище только её хэш
   (SHA-256), `player_id`, `expires_at`, флаг использования — саму
   метку на диске/в памяти после ответа не держим.
2. Ответ — готовый адрес `https://<домен>/admin#t=<метка>` или сама
   метка; клиент открывает вкладку. Метка во фрагменте: в логи сервера
   и в `Referer` не попадает.
3. Страница панели читает `#t=…`, стирает его из адресной строки
   (`history.replaceState`) и вызывает `POST /api/v1/admin/session` с
   меткой в теле. Сервер атомарно проверяет: хэш совпал, срок не вышел,
   не использована — и помечает использованной в той же операции
   (один воркер, но обработчики async: пометка до первого `await`).
   В ответ — короткий сеанс.
4. Все ответы обмена и входа — с `Cache-Control: no-store`.

### Срок жизни и хранилище

- Срок жизни метки: **60 секунд** (нужно только пережить открытие
  вкладки; набрать её руками не требуется). Одноразовая.
- Сеанс панели: короткий JWT (порядка 15–30 минут) или отдельный тип
  токена. Вкладка держит его в `sessionStorage`: переживает F5 в той же
  вкладке и умирает вместе с ней. Строже — только в памяти страницы,
  но тогда любое обновление панели требует новой ссылки из Mini App;
  рекомендую `sessionStorage` как баланс.
- Права проверяются **по базе при каждом запросе** (юнит 3 добавит
  таблицу выданных прав; `require_admin` будет читать `.env` + таблицу):
  снятый администратор теряет доступ сразу, не дожидаясь конца сеанса.
- Хранилище меток — **в памяти процесса** (один воркер, см. Q3):
  словарь «хэш → запись» с очисткой просроченных. Перезапуск backend
  обнуляет выданные, но ещё не использованные ссылки — пользователь
  просто выпускает новую; выданные сеансы (JWT) рестарт переживают.
  Если воркеров когда-нибудь станет больше одного — хранилище переезжает
  в БД без смены протокола. Таблица в БД — допустимая, но более
  дорогая альтернатива (новая миграция).

### Открытие вкладки — три варианта по итогам пробы

- **Вариант А (желателен):** метку выпускают заранее (при открытии блока
  «Админ» или по первому наведению на кнопку), а по щелчку —
  `window.open(готовый_адрес, '_blank')` синхронно. Щелчок не ждёт сеть —
  блокировки точно нет. Минус: метки могут выпускаться впустую.
- **Вариант Б:** по щелчку сначала `await` выдачи метки, потом
  `window.open`. Риск блокировки всплывающего окна — проба (кнопка «б»)
  измеряет его на живом ВК.
- **Вариант В (запасной, без блокировок по определению):** обычная ссылка
  `<a target="_blank" rel="noopener">`, в `href` которой готовый адрес с
  меткой появляется после её выдачи («кнопка становится активной»).
  Пользовательский переход по существующей ссылке браузер не блокирует
  никогда.
- `rel="noopener"` во всех случаях: новой вкладке не нужен
  `window.opener` обратно в iframe (проба покажет, есть ли он вообще).

### Хранилище iframe и вкладки — что решает проба

Непроверенное место: видна ли новой вкладке `localStorage`/`sessionStorage`
нашего домена, записанная внутри iframe ВК. Если видна — теоретически
метку можно было бы передать через хранилище вообще без фрагмента в URL.
Если хранилище изолировано (в современных браузерах сторонние iframe
получают партиционированное хранилище — точное поведение на vk.com у нас
**НЕ ПРОВЕРЕНО**) — остаётся схема с `#t=`. Проба (страница
`admin-probe.html`) измеряет: дожил ли фрагмент до вкладки, есть ли
`window.opener`, что в `document.referrer`, видны ли метки iframe,
можно ли вкладке писать своё хранилище.

### Заголовки безопасности для `/admin` (описание для юнита 4, `deploy/Caddyfile` не трогаем)

Сейчас на весь сайт сознательно не ставятся `X-Frame-Options`/
`frame-ancestors` — приложение живёт в iframe ВК, неверное значение
покажет игрокам белый экран (Caddyfile, комментарий; `deploy.md` §5).
Для панели нужен отдельный блок `handle /admin*` с:

- `X-Frame-Options: DENY` и/или `Content-Security-Policy: frame-ancestors 'none'`
  — панель нельзя встроить ни в какой iframe, включая сам ВК;
- `Referrer-Policy: no-referrer` — адрес панели не уходит наружу;
- `Cache-Control: no-store` — страница и данные не кэшируются.

Важно: заголовки ставятся **только** на путь панели — общий `handle`
должен остаться без них, иначе умрёт Mini App.

### Вторая точка входа или отдельная страница

`frontend/vite.config.ts` сейчас описывает одну точку входа
(`index.html`); Caddy отдаёт любой реальный файл из `/srv` раньше
SPA-fallback `try_files {path} /index.html` (это и позволяет работать
`admin-probe.html` из `frontend/public/`). Варианты:

- **Отдельный статический файл** `frontend/public/admin/index.html` —
  ноль сборки, но панель из 12 юнитов быстро упрётся в ручной JS.
  Также `/admin` без расширения сейчас попадёт в fallback на Mini App —
  понадобится `try_files {path} {path}/index.html /index.html`
  (правка Caddyfile, юнит 4).
- **Вторая точка входа Vite** (`build.rollupOptions.input` →
  `{ main: index.html, admin: admin.html }`): в `dist` появится
  `admin.html` со своим бандлом — чистый React-вход без vk-bridge и без
  веса Mini App. Рекомендую этот путь: панель — отдельное приложение,
  а механизм отдачи файла уже доказан пробой.

### Рекомендация: основной путь / запасной

- **Основной:** одноразовая ссылка из Mini App — `POST /panel-link` →
  метка в `#`-фрагменте → обмен на короткий сеанс; открытие вкладки
  синхронно по щелчку с заранее выпущенной меткой (вариант А), если
  проба покажет блокировку — активная `<a target="_blank">` (вариант В).
- **Запасной:** вход через VK ID на странице панели. Держать только если
  проба покажет, что вкладка из окна ВК не открывается вовсе: по
  документации он требует VK Бизнес ID и подтверждения профиля бизнеса
  за 60 дней — для Project Owner это тяжелее, чем «просто без
  модерации», и ради редкого отказа блокиратора овчинка выделки не
  стоит.

## Что проверяет живая проба (чек-лист Project Owner)

1. Кнопка «а»: вкладка открылась сразу по щелчку; в отчёте виден
   `#t=probe`, `window.opener`, `referrer`, метки хранилища.
2. Кнопка «б»: то же, но после сетевого запроса — открылась или
   браузер заблокировал (см. строку результата рядом с кнопкой).
3. Ссылка «в»: обычный переход; сравнить `referrer`/`opener` с «а».
4. Из каждой вкладки — скопировать текстовый отчёт и прислать в чат.
