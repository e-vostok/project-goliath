## б. Хранение: PostgreSQL против файлов на диске

Факты контура (**ПОДТВЕРЖДЕНО**, файлы):

- `docker-compose.prod.yml`: у `backend` нет ни одного тома; у `caddy`
  тома только `caddy_data`/`caddy_config` (сертификаты); единственный
  том данных — `pgdata` у `db`. Общего файлового тома между backend и
  Caddy **нет**.
- `deploy/Caddyfile`: Caddy отдаёт только файлы из `/srv` внутри своего
  образа (собранный фронтенд) и проксирует `/api/*` в `backend:8000`.
  Файлы из контейнера backend он отдать физически не может.
- `deploy/backup.sh`: единственный объект копирования —
  `pg_dump --format=custom` с проверкой `pg_restore --list`; внешняя
  копия — тот же дамп через age+rclone. Файлы на диске не сохраняются.
- `backend/tests/core/admin/test_admin_table_coverage.py`: каждая
  таблица в `Base.metadata` обязана быть классифицирована (`reset` /
  `player_delete` / `kept` с причиной) — новая таблица без записи роняет
  тест. Файлы на диске этот тест не видит.
- `deploy/`, `docker*`, `Dockerfile*` — запрещённые для агента пути
  (devin_rules.md) и перечислены в рисках версии.

Сравнение по требуемым осям:

| Ось | Картинки в базе (`nation_images`, bytea) | Файлы на диске |
|---|---|---|
| Бэкап/восстановление | Входят в `pg_dump` автоматически; проверка и внешняя копия уже есть | Нужны: том в compose, tar-шаг в `backup.sh`, шаг восстановления, правка `restore_check.sh` — всё запрещённые пути |
| Удаление | Одна транзакция с удалением нации/игрока — сирота невозможна по построению | Файл может пережить строку в базе и наоборот; нужна сборка мусора |
| Сироты | Невозможны | Возможны при падениях; отдельный механизм поиска |
| Правки деплоя | Ноль | Новый named volume + `deploy/*` — запрещённые пути, действия Project Owner на сервере |
| Раздача | Через приложение | Всё равно через приложение (Caddy тома не видит) — выигрыша нет |
| Память одного воркера | Строка ~≤150 КБ поднимается на запрос; суммарно при 200 государствах ≈ 25–45 МБ в базе | Тело тоже проходит через тот же воркер |
| Покрытие «забытой таблицей» | Принудительное: тест не даст забыть reset/player_delete | Тест не видит файлов — гарантии нет |

**Рекомендация: хранить в PostgreSQL.** Отдельная таблица
`nation_images` в `00_core` (FK к `nations.id` — корневая таблица
своего модуля, инвариант не нарушается): bytea не попадает в горячие
выборки `nations`, строка сама несёт ключ содержимого (sha256).
Единственная цена — рост дампа на ~25–45 МБ при полном парке
государств (оценка по замерам раздела «в»: картинка 5–150 КБ, миниатюра
<1 КБ; **НЕ ПРОВЕРЕНО** на реальном парке — государств пока единицы).

## в. Формат, размер, безопасность разбора

### Замеры (Pillow 13.0.0; синтетика: «флаг» — плоские цвета с эмблемой, «фото» — градиент с шумом)

| Картинка | PNG opt | JPEG q85 | JPEG q95 | WebP q85 | WebP q95 | WebP lossless |
|---|---|---|---|---|---|---|
| Флаг 600×400, плоский | 2 240 Б | 14 502 Б | 20 963 Б | 5 636 Б | 7 598 Б | 814 Б |
| Флаг 600×400, «фото» | 311 092 Б | 74 566 Б | 130 713 Б | 56 232 Б | 101 550 Б | 258 278 Б |
| Портрет 600×800, плоский | 4 094 Б | 23 390 Б | 33 509 Б | 9 436 Б | 13 706 Б | 1 478 Б |
| Портрет 600×800, «фото» | 608 933 Б | 145 357 Б | 256 483 Б | 107 976 Б | 178 542 Б | 502 928 Б |
| Миниатюра флага 96×64 | PNG 2 105 Б | — | — | WebP q80 646 Б | — | — |
| Миниатюра портрета 120×160 («фото») | PNG 18 164 Б | — | — | WebP q80 294 Б | — | — |

**ПОДТВЕРЖДЕНО** как замер на синтетике; на настоящих фотографиях
соотношения могут отличаться, вывод «WebP q85 самый маленький из
пригодных повсеместно» устойчив — **НЕ ПРОВЕРЕНО** на реальных файлах
Project Owner. Вывод из таблицы: для плоских флагов PNG иногда меньше
lossy-WebP, но единый выходной формат важнее микро-экономии — плоский
флаг в WebP это всё равно 5–10 КБ.

Время конвейера «прочитать → распаковать → повернуть по EXIF →
обрезать/уменьшить → записать WebP» (**ПОДТВЕРЖДЕНО** замером,
медиана 3 прогонов):

- Источник JPEG 4000×2667 (10,7 МП, файл 5,6 МБ): header ~1 мс,
  распаковка ~60–70 мс, resize LANCZOS ~85 мс, запись WebP ~25–100 мс —
  итого **~170–250 мс чистого CPU**.
- Источник 25 МП (файл 13 МБ): итого **~360 мс**.
- Ловушка «маленький файл — большие пиксели»: PNG 9000×9000 одного
  цвета весит 253 КБ, а распаковывается в **~324 МБ** пикселей
  (81 МП × 4 Б) — предел в мегабайтах тела запроса от этого не защищает.

### Решения по приёму

- **Проверка типа — по содержимому.** `Image.open` читает сигнатуру
  (магические байты) и выставляет `im.format`: PNG-байты под любым
  именем дают `format='PNG'`, WebP-байты — `'WEBP'`, текст/HTML —
  `UnidentifiedImageError`, обрезанный файл — `OSError
  "image file is truncated"` (**ПОДТВЕРЖДЕНО** замером). Расширение
  имени файла и клиентский `Content-Type` в решении не участвуют.
- **Принимаем:** JPEG, PNG, WebP. Не принимаем GIF (анимация и кадры —
  лишняя ветка; отказ понятным сообщением), SVG (векторный — потенциал
  встроенного контента, не растр) и всё прочее.
- **Предел тела запроса: 5 МБ.** Читаем с отсечкой: сперва
  `Content-Length` (нет или > лимита — отказ), потом само тело
  по кускам до границы — защита и от chunked без длины.
- **Защита от «бомб» до распаковки.** У `Image.open` размер известен
  из заголовка до `load()` — **ПОДТВЕРЖДЕНО**: `im.size` читается за
  ~1 мс без декодирования. Отказ, если `w*h > 25 000 000` или
  `max(w,h) > 8000`. Собственный предел Pillow оставляем как есть:
  `Image.MAX_IMAGE_PIXELS = 89 478 485`, ошибка `DecompressionBombError`
  при > 178 956 970 пикселей (**ПОДТВЕРЖДЕНО** замером — PNG 30 000×
  30 000 отклонён ей) — это последняя сеть, наш предел ниже и
  срабатывает раньше.
- **Всегда перекодируем** в WebP q85, RGB: поворот по EXIF
  (`exif_transpose`), приведение к точному размеру. Метаданные не
  переносятся — **ПОДТВЕРЖДЕНО**: при сохранении без параметра `exif`
  теги 271/306 и GPS-IFD исчезли, `icc_profile` тоже (`None`). Альфа-
  канал PNG сводим на белый фон — чёрные ореолы на краях исчезают.
- **Цикл событий не блокируем.** 170–360 мс CPU на одну картинку —
  для единственного воркера это заметная пауза всех запросов и тика.
  Разбор и пережатие выполняются в пуле потоков
  (`asyncio.to_thread`/`run_in_executor`) под `asyncio.Semaphore(1)`:
  одна картинка за раз, пик памяти ~100–325 МБ на распакованный
  источник (**ПОДТВЕРЖДЕНО** по замерам; 4 ГБ сервера хватает с
  запасом, две-три параллельные распаковки уже рискованны).
- **Зависимости:** Pillow — новая зависимость backend (ТЗ единицы 5
  разрешает явно; в `pyproject.toml` её нет — **ПОДТВЕРЖДЕНО**).
  `python-multipart` можно НЕ брать: принимать тело как есть
  (`Content-Type: application/octet-stream`, `await request.body()`
  с отсечкой по байтам) вместо multipart-формы — проще и честнее
  лимит. Решение окончательно за ТЗ единицы 5.

### Эталонные размеры и окно

- **Флаг 600×400 (3:2), портрет 600×800 (3:4).** Те же пропорции, что у
  нынешнего каталога 300×200/300×400 — **ПОДТВЕРЖДЕНО** (заглушки
  измерены: `flag_placeholder_*.png` — 300×200, `portrait_placeholder_*
  .png` — 300×400); двукратный запас под плотные экраны.
- Текст окна: «картинка 600×400 вставляется без обрезки» для флага и
  «600×800» для портрета — дословно как в цели версии.
- **Картинка другого размера:** в окне — рамка обрезки с закреплённой
  пропорцией (3:2 / 3:4). Сервер на клиентскую обрезку не полагается:
  всегда сам центрально обрезает до пропорции и ресайзит до точного
  размера — рамка нужна для удобства, а не для корректности.

## г. Раздача и кэш

- **Только через приложение**: `GET /api/v1/images/{sha256}/{full|thumb}`.
  Через Caddy отдать нельзя — общего тома нет (**ПОДТВЕРЖДЕНО**,
  compose). Ответ: `Content-Type: image/webp`, тело из bytea.
- **Публичный доступ, без Bearer.** Картинки показываются обычным
  `<img src>` — **ПОДТВЕРЖДЕНО**: `NationLabel.tsx` (стр. 41–42) и
  `CreateNationTabSymbols.tsx` (стр. 285–286) ставят URL в `src` тега
  `img`; `<img>` не умеет отправлять `Authorization`. Содержимое не
  секретное — оно и так видно всем игрокам; каталожные картинки уже
  сегодня публичны под `/assets/`.
- **Адрес по содержимому**: sha256 результата после пережатия. Замена
  загрузки — новый адрес; старый становится 404. Окна и Реестр получают
  адрес в DTO государства (как сейчас `flag_url`) — кэш записей данных
  не пострадает: DTO сами `no-store`/`no-cache`.
- **Кэш на 200:** `Cache-Control: public, max-age=86400`; на 404 —
  `Cache-Control: no-store`. Последствие удаления администратором:
  новые зрители картинку не получат сразу; у уже загрузившего она может
  оставаться в кэше браузера до 24 часов — вдвое быстрее требования ВК
  «не позднее 48 часов» (п. 2.5.3). Вечный `immutable` (как у
  `/api/v1/map/geometry/{version}`) сюда не подходит именно по этой
  причине — риск из раздела 4 файла версии. `ETag = sha256` даёт дешёвый
  304 при перевалидации.
- **Миниатюра** `thumb` хранится в той же строке (вторая bytea-колонка)
  — пережимать на каждый запрос не нужно; таблицы Реестра берут
  `thumb`, подэкран «Государство» и «Штаб» — `full`.

## д. Квоты

- **На государство**: одна загрузка флага и одна портрета — уникальный
  ключ `(nation_id, kind)`, `kind ∈ {flag, portrait}`. Повторная
  загрузка перезаписывает строку: прежний sha256 умирает (URL → 404),
  каталожный выбор остаётся нетронутым.
- **Суточный предел на игрока: 10 успешных загрузок.** Считаем в
  отдельной таблице-счётчике `(player_id, дата_UTC, count)` — инкремент
  в той же транзакции с записью картинки; считаются только успешные
  (отклонённые по типу/размеру не расходуют квоту). Число — в
  `configs/00_core.yaml` (`images.uploads_per_day`, схема с жёсткими
  границами по Config-Safe Pattern). Это техническая защита ресурсов,
  не блокировка по содержанию — формулировка из журнала решений версии.
  Обоснование числа: худший случай 10 × 5 МБ входа ≈ 50 МБ/сутки на
  игрока — ничтожно для диска и дампа, а для «покрутить кадр» десятка
  с запасом хватает.
- Обе новые таблицы обязаны попасть в `TABLE_COVERAGE`
  (`test_admin_table_coverage.py`): `nation_images` — `reset` +
  удаление при удалении нации и игрока; счётчик — `player_delete`.
  Это не напоминание, а принуждение: без записи тест упадёт —
  **ПОДТВЕРЖДЕНО** чтением теста.

## е. Резервные копии и восстановление

- При выбранной схеме (bytea) картинки входят в дамп сами:
  `pg_dump --format=custom` включает blob-данные таблиц; `backup.sh`
  уже проверяет читаемость дампа `pg_restore --list` и шлёт
  зашифрованную копию наружу — **ПОДТВЕРЖДЕНО** чтением `backup.sh`.
  Менять ничего не нужно: ни `backup.sh`, ни compose, ни
  `restore_check.sh` — единица 11 версии переводится в `dropped`
  (причина уже записана в файле версии).
- Рост дампа — десятки мегабайт (см. оценку в «б»); 14 ежедневных
  копий ≈ +0,3–0,6 ГБ в худшем случае — при «>3 ГБ свободно» по
  чек-листу приемлемо (**НЕ ПРОВЕРЕНО** для точного объёма: зависит от
  числа загрузок).
- Проверка в приёмке (единица 12): после бэкапа убедиться, что в дампе
  есть строки `nation_images` и что восстановленная копия их отдаёт —
  по существующей процедуре `restore_check.sh`.
- Если бы были выбраны файлы: потребовались бы named volume у backend,
  tar-шаг в `backup.sh`, шаг восстановления и хранение рядом с дампом —
  все затронутые пути для агента запрещены, риск рассинхрона
  «дамп есть — файлов нет» сохранялся бы навсегда.
