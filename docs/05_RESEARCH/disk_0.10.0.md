# Диагностика диска сервера — версия 0.10.0, единица 1

Статус: закрыто в 0.10.0 (единица 1)

Дата замера: 24.10.2026. Замер и ручная очистка — Project Owner на боевом
сервере, скрипт диагностики — `deploy/disk_report.sh` (только чтение).

## Факты

- Корневой диск — 38 ГБ. До чистки: занято 25 ГБ, свободно 14 ГБ.
- Причина — **кэш сборки Docker (~19 ГБ)**: `deploy/deploy.sh` каждый
  деплой выполняет `docker compose ... --build` и никогда не чистит кэш.
- На сервере образы хранит containerd (containerd image store);
  `/opt/goliath` — откреплённый (detached) checkout тега v0.9.0.

## Что сделал Project Owner вручную (по порядку)

| Команда | Освобождено |
|---|---|
| `docker builder prune -f --filter until=72h` | 3,246 ГБ |
| `docker image prune -f` | 0 Б (образы — не проблема) |
| `docker builder prune -a -f --filter until=72h` | 5,077 ГБ |

Итог: занято 25 ГБ → 17 ГБ, свободно 14 ГБ → 22 ГБ (диск занят на 44 %).
Всего освобождено ≈ 8,3 ГБ.

## Уроки

- Без `-a` Docker оставляет большинство «reclaimable»-записей кэша —
  работает именно вариант с `-a`.
- Работающие контейнеры, используемые образы и том базы
  `goliath_pgdata` не пострадали.
- **Никогда не использовать `docker system prune` и `--volumes`** — это
  ставит под угрозу том базы.

## Решение

Автоматическая очистка кэша сборки старше 72 часов в конце каждого
успешного деплоя: `deploy/deploy.sh`, функция `prune_build_cache`
(вызывается после проверки сайта, до строки «Deploy OK»). Очистка —
best-effort: её сбой печатает предупреждение и не влияет на деплой.
72 часа выбраны, чтобы кэш последних дней оставался тёплым и пересборка
при откате была быстрой. Ручная команда для аварий — runbook,
раздел 14.1.
