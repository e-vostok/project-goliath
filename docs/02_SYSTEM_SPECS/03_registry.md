## 0. Принятые архитектурные решения (отклонения от Bible и от «буквы» Prompt 2)

**D1. Границы шкал — константы модели, а не баланс.** Минимальный уровень (1) и границы судейского рейтинга (−100…+100) — свойства шкалы, закреплённые в БД проверками `CHECK` (конфиг не может изменить ограничение базы). Они объявлены один раз как константы в коде `00_core` (`LEVEL_MIN`, `JUDGE_RATING_MIN`, `JUDGE_RATING_MAX`). В `configs/03_registry.yaml` те же числа повторены только как параметры отрисовки шкалы (`scale_min`, `scale_max` столбца типа `gauge`); тест сверяет конфиг с константами `00_core` (Приложение T, группа «Конфиг»).

**D2. Номера не хранятся.** Порядковые номера игроков и государств вычисляются при чтении (3.2, 3.3). Колонок номеров нет. Номер игрока постоянен, потому что игроки не удаляются, а `players.created_at` неизменен; номер государства — место среди существующих.

**D3. Собственный клиент ВК, существующий ключ.** Для `users.get` модуль содержит свой небольшой клиент на `httpx` (по образцу `02_bot/vk_client.py`), а не вызывает `02_bot`. Ключ — существующая переменная окружения `VK_GROUP_TOKEN`. Новых переменных окружения нет. Работа профилей не зависит от `BOT_ENABLED`: ключ есть — профили запрашиваются. Ключа нет — профили выключены (один WARNING в журнал), таблицы работают с запасным видом (Bible, раздел 5).

**D4. Профили — фоновая задача, а не запрос на открытие таблицы.** Открытие таблицы читает только сохранённые профили и никогда не ждёт ВК (INV-R6). Получение идёт в фоновой задаче процесса сервера; открытие таблицы лишь будит её, если есть игроки без профиля или с просроченным профилем (2.4).

**D5. Две миграции.** `0008` — расширение `00_core` (колонки игрока и государства), `0009` — таблица профилей модуля. Обе в классе NEEDS LEAD AI REVIEW.

**D6. Таблица целиком одним ответом.** Сервер отдаёт все строки таблицы (до предела `limits.max_rows_per_table`), сортировка, фильтры и поиск выполняются в браузере (Bible, 2.3–2.4). Формат ответа не мешает позднему переходу на серверную обработку.

**D7. «В проекте с» — календарная дата по московскому времени.** День вычисляется в зоне `tick.tick_timezone` из `00_core` (сейчас `Europe/Moscow`), чтобы день присоединения совпадал с игровыми сутками.

**D8. Нет админ-правки уровня и рейтинга.** Решение Project Owner 13.10.2026: на старте заглушки; форма правки в панели администратора не создаётся. Значения меняются только будущими механиками через публичные функции `00_core`.

**D9. Реестр не регистрирует reset-хук.** Профили ВК описывают людей, а не состояние мира; сброс мира их сохраняет. Регистрируется только хук просмотра состояния (5.4).

## ЧАСТЬ 1: ДОМЕННАЯ МОДЕЛЬ

### 1.1. Таблица БД модуля

#### `registry_vk_profiles` — сохранённый профиль ВК игрока

| Поле | Тип | Правила |
| :-- | :-- | :-- |
| `player_id` | `String(36)` | PK; FK → `players.id` `ON DELETE CASCADE` |
| `status` | `String(12)` NOT NULL, по умолчанию `PENDING` | `PENDING` / `OK` / `UNAVAILABLE` (`ck_registry_vk_profiles_status`) |
| `first_name` | `String(64)` NULL | имя; NULL, пока не получено |
| `last_name` | `String(64)` NULL | фамилия |
| `photo_url` | `String(1024)` NULL | адрес малой аватарки; только `https` |
| `fetched_at` | `DateTime(timezone=True)` NULL | момент последнего ответа ВК по этому игроку; NULL до первого |
| `next_attempt_at` | `DateTime(timezone=True)` NOT NULL | когда запрашивать снова; у новых записей — момент создания |

Индекс `ix_registry_vk_profiles_next_attempt` по `next_attempt_at`. Других таблиц у модуля нет. Первичный ключ без суррогата (как `bot_consents`). Тип первичного ключа и обработка `DateTime(timezone=True)` на SQLite — по правилам миграций `0002`/`0007` (урок naive vs aware datetime).

### 1.2. Изменения в `00_core` (миграция `0008`)

Аддитивно, существующие данные сохраняются:

| Таблица | Колонка | Тип и правила |
| :-- | :-- | :-- |
| `players` | `level` | `Integer` NOT NULL, `server_default 1`, `ck_players_level_min`: `level >= 1` |
| `players` | `judge_rating` | `Integer` NOT NULL, `server_default 0`, `ck_players_judge_rating_range`: `judge_rating BETWEEN -100 AND 100` |
| `nations` | `created_turn` | `BigInteger` NOT NULL (без значения по умолчанию после заполнения), `ck_nations_created_turn_min`: `created_turn >= 0` |

**Заполнение `nations.created_turn` для существующих государств.** `tick_log.turn_number` записывает номер хода, который *наступает* после тика (`current_turn + 1` на момент тика), поэтому завершённый тик с номером $T$ означает, что игра перешла на ход $T$ в момент `finished_at`.

$$created\_turn(n) = \max\{\, T_k \;:\; status_k = \text{COMPLETED},\; finished\_at_k \le created\_at(n) \,\},\qquad \max\varnothing = 0$$

Алгоритм миграции: добавить колонку как nullable → в Python (через `op.get_bind()`) вычислить значение для каждого государства, нормализуя «наивные» и «осведомлённые» метки времени к UTC перед сравнением → установить NOT NULL (`batch_alter_table` для SQLite). Значение приблизительное, если ходы запускались вручную; для новых государств точное (1.4).

**Константы** (`modules/_00_core/player_stats.py`, новый файл): `LEVEL_MIN = 1`, `JUDGE_RATING_MIN = -100`, `JUDGE_RATING_MAX = 100`, `LEVEL_DEFAULT = 1`, `JUDGE_RATING_DEFAULT = 0`. Модели и проверки миграции используют их.

### 1.3. Миграция `0009` (модуль `03_registry`)

Создаёт `registry_vk_profiles` с индексом и CHECK; downgrade удаляет таблицу и ничего больше. Модуль подключается в `alembic/env.py` и в тесты дрейфа моделей (`test_model_migration_drift*.py`).

### 1.4. Что модуль читает у других (только публичные функции сервисов `00_core`)

Новые функции чтения добавляются в `service.py` ядра отдельным коммитом (Приложение B). Они только читают и не делают commit.

```python
@dataclass(frozen=True)
class PlayerRegistryRow:
    player_id: str           # не отдаётся клиенту (INV-R2)
    vk_user_id: int          # не отдаётся клиенту (INV-R2); нужен для запроса профиля
    created_at: datetime
    level: int
    judge_rating: int
    nation_id: str | None
    nation_name: str | None
    nation_color: str | None

@dataclass(frozen=True)
class NationRegistryRow:
    nation_id: str
    name: str
    color_hex: str
    created_turn: int
    created_at: datetime
    province_count: int

PlayerService.list_for_registry(session) -> list[PlayerRegistryRow]   # порядок: created_at, id
NationService.list_for_registry(session) -> list[NationRegistryRow]   # порядок: created_turn, created_at, id
```

`province_count` считается как число строк `provinces` с `nation_id = nation.id` (морская зона не может иметь владельца: `ck_provinces_sea_unowned`). Игровую дату считает существующая `compute_game_date(turn, CoreConfig)`; зону и календарь Реестр берёт из `CoreConfig`, загруженного тем же `CoreConfig.get_default_config_path()`, что и `router.py` ядра.

`NationService.create` записывает `created_turn` = `game_clock.current_turn` той же транзакции (через существующий `_current_turn(session)`), как `OwnershipChange.turn`. `NationService.update` поле не меняет (INV-R9).

### 1.5. Связи и переменные окружения

Единственный внешний ключ модуля — `registry_vk_profiles.player_id → players.id`. Новых переменных окружения нет; используется `VK_GROUP_TOKEN` (секрет, не попадает в журнал и в `repr`).

## ЧАСТЬ 2: ИНВАРИАНТЫ, FSM И МЕСТО В TICK DAG

### 2.1. Место в Tick DAG

**Нет.** `tick_phase: NONE`. Модуль не регистрирует обработчик ни в одной из пяти фаз `TickPhase` и не читает состояние тика. Обоснование: Реестр ничего не пересчитывает при смене хода — он собирает таблицу из зафиксированных данных в момент запроса; получение профилей ВК — сетевая операция, которая не должна быть частью атомарной транзакции хода (сбой ВК не может откатить ход).

### 2.2. Инварианты

- **INV-R1. Только чтение чужих данных.** Модуль не пишет в таблицы `00_core`, `01_map`, `02_bot`; единственная таблица записи — `registry_vk_profiles`. Чтение — только через публичные функции (1.4).
- **INV-R2. Приватность идентификаторов.** Ответы API не содержат `vk_user_id` и `player_id`. Строка игрока адресуется ключом `p<номер>`. В ответе нет ссылок на страницы ВК.
- **INV-R3. Config-Safe.** Ошибка конфига или ссылка на неизвестный источник останавливает запуск (2.5).
- **INV-R4. Предел строк.** Ответ содержит не больше `limits.max_rows_per_table` строк; при превышении `truncated = true`, `total` — полное число.
- **INV-R5. Нумерация.** Правила 3.2 и 3.3 соблюдаются при любой сортировке и фильтрах (номер принадлежит строке).
- **INV-R6. Сбой ВК изолирован.** Исключение или ошибка в фоновой задаче профилей никогда не меняет код ответа API, не задерживает ответ и не влияет на ход; задача перехватывает все исключения, кроме `CancelledError`.
- **INV-R7. Имя всегда непустое.** Каждая ячейка типа `person` содержит непустое `name` (при отсутствии профиля — запасное имя).
- **INV-R8. Границы шкал** обеспечиваются на уровне БД (1.2).
- **INV-R9. `created_turn` неизменяем** после создания государства.
- **INV-R10. Одинаковый вид для всех.** Состав строк и значений не зависит от того, кто запрашивает (все авторизованные игроки видят одно и то же).

### 2.3. FSM профиля (`registry_vk_profiles.status`)

```text
(нет записи) --создание записи фоновой задачей--> PENDING
PENDING     --ВК вернул пользователя без deactivated--> OK
PENDING     --ВК вернул deactivated или не вернул пользователя--> UNAVAILABLE
OK          --обновление успешно--> OK
OK          --ВК вернул deactivated или не вернул--> UNAVAILABLE   (имя и фото последнего успешного ответа сохраняются)
UNAVAILABLE --ВК вернул пользователя без deactivated--> OK
любой       --сбой запроса--> без изменения status; next_attempt_at = now + failure_retry_minutes
```

После любого ответа ВК (успешного или `UNAVAILABLE`): `fetched_at = now`, `next_attempt_at = now + ttl_hours`. Имена и фото в состоянии `UNAVAILABLE` не перезаписываются данными ответа.

### 2.4. Фоновая задача профилей

**Режимы:** `OFF` (`profiles.enabled = false`), `NO_TOKEN` (включено, но `VK_GROUP_TOKEN` пуст; один WARNING), `RUNNING`. Задача запускается в `lifespan` после планировщика тика и бота, останавливается отменой при завершении сервера. Режимы `OFF` и `NO_TOKEN` ничего не запускают и не влияют на запуск сервера.

**Цикл** (каждые `profiles.wake_interval_minutes` или по пробуждению, см. ниже):

1. *Создание записей.* Для игроков без строки в `registry_vk_profiles` вставить строки `PENDING` с `next_attempt_at = now` (пакетная вставка, идемпотентная по PK).
2. *Выбор.* Взять до `profiles.batch_size` строк с `next_attempt_at <= now`, по возрастанию `next_attempt_at`.
3. *Запрос и применение* — алгоритм 3.4. Результат применяется одной транзакцией на пакет.
4. Если просроченные строки остались — пауза `profiles.batch_pause_seconds` и следующий пакет; иначе сон до следующего пробуждения.

**Пробуждение событием.** Модуль-уровневый `asyncio.Event`. Построение таблицы «Игроки» (3.2) устанавливает его, если среди игроков есть тот, у кого записи нет, либо `next_attempt_at <= now`. Строки с отложенным повтором (`next_attempt_at` в будущем) событие не устанавливают, поэтому недоступный ВК не создаёт нагрузки от открытия таблиц.

### 2.5. Порядок запуска (`startup_registry()`)

Вызывается в `lifespan` **после** всех остальных `startup_*` (чтобы будущие модули успели зарегистрировать источники), синхронно, без БД и сети, идемпотентно:

1. Загрузить и проверить `configs/03_registry.yaml` (`RegistryConfig`) — всегда, даже при `profiles.enabled = false`.
2. Зарегистрировать встроенные источники `players` и `nations` (Приложение A).
3. **Проверить конфиг против реестра источников:** для каждой таблицы существует источник с ключом `tables[].source`; для каждого столбца `columns[].source` входит в `provides` источника. Любое несоответствие — `RegistryConfigError`, запуск прерывается (INV-R3).
4. Зарегистрировать хук состояния (5.4).

Фоновая задача стартует отдельно (`start_profile_worker_if_ready`), после планировщика.

### 2.6. Реестр источников (публичный API для будущих модулей)

Модуль-владелец данных подключает столбец или таблицу без правки интерфейса: регистрирует источник таблицы в своём `startup_*` до `startup_registry()` (Приложение A). Одна таблица — один источник; источник заявляет набор ключей значений `provides`. Столбец конфига ссылается на ключ из `provides`. Регистрация повторного ключа заменяет предыдущую (как `register_nation_created_hook`).

## ЧАСТЬ 3: АЛГОРИТМЫ

### 3.1. Сборка таблицы (`build_table(session, table_id)`)

1. Найти таблицу в конфиге; нет — `REGISTRY_TABLE_NOT_FOUND`.
2. Вызвать `load(session)` источника: список `RegistryRow(key, cells)`.
3. Проверить каждую ячейку выбранных столбцов по типу (3.6); несоответствие или отсутствие ключа — `RegistryProviderError` (`REGISTRY_PROVIDER_FAILED`, журнал: идентификатор таблицы и столбца, без значений).
4. Отсортировать по `default_sort` (ключи сравнения — 3.7; пустые значения в конец; устойчивая сортировка).
5. Если строк больше `limits.max_rows_per_table`: оставить первые, `truncated = true`.
6. Вернуть `total`, `truncated`, `generated_at` и строки только тех ключей, что перечислены в столбцах конфига (лишние ключи источника не отдаются).

### 3.2. Источник `players`

Ключи `provides`: `number`, `player`, `joined`, `level`, `judge_rating`, `nation`.

$$number(p) = 1 + \#\{\, q : (created\_at_q,\ id_q) < (created\_at_p,\ id_p) \,\}$$

То есть позиция в порядке `PlayerService.list_for_registry` (одно число на игрока, считается `enumerate` по уже упорядоченному списку). Ключ строки: `p<number>`.

- `player` — ячейка `person`. Профиль берётся из `registry_vk_profiles` одним запросом для всех игроков. Имя: `"{first_name} {last_name}"` без краевых пробелов; пустое или нет профиля — `fallback_name_template.format(number=number)`. `avatar_url` — `photo_url` при `status = OK`, иначе `None`. `is_fallback = true`, когда имя запасное.
- `joined` — ячейка `date` (3.5).
- `level`, `judge_rating` — числа; `nation` — `{name, color, flag_url}` либо `null` (`flag_url = null`, пока загрузки флагов государств нет).

### 3.3. Источник `nations`

Ключи: `number`, `name`, `flag`, `formed`, `provinces`.

$$number(n) = 1 + \#\{\, m : (created\_turn_m,\ created\_at_m,\ id_m) < (created\_turn_n,\ created\_at_n,\ id_n) \,\}$$

Ключ строки — `nation_id` (стабилен в пределах ответа). `flag` — `{color: color_hex, image_url: null}` (заглушка; когда появится загрузка флагов, источник вернёт `image_url`). `formed` — ячейка `date` с `key = created_turn` и `text` = игровая дата словами (3.5). `provinces` — `province_count`.

### 3.4. Получение профилей ВК (шаг 3 цикла 2.4)

Запрос: `POST {profiles.api_base_url}/users.get`, заголовок `Authorization: Bearer <VK_GROUP_TOKEN>`, тело `application/x-www-form-urlencoded`: `user_ids` (идентификаторы ВК через запятую), `fields` = `profiles.photo_field`, `v` = `profiles.api_version`. Ожидание — `profiles.http_timeout_seconds`.

Разбор ответа (по итогам REG-0, `03_registry_vk_facts.md`, R1–R6):
- Пользователь возвращён без `deactivated` и без `hidden = 1`: `status = OK`; `first_name`, `last_name`, `photo_url` обновляются.
- Возвращён с `deactivated` (`deleted` или `banned`) либо с `hidden = 1`, либо запрошенного идентификатора нет в ответе: `status = UNAVAILABLE`; имена и фото не меняются. У `deactivated`-элемента необязательные поля (фото) не приходят; содержимое его `first_name`/`last_name` не документировано, поэтому не применяется.
- **Ошибки, относящиеся к конкретному игроку** — 30 («профиль приватный») и 113 («неверный идентификатор»): пакет делится пополам и каждая половина запрашивается заново (рекурсивно); для одного идентификатора результат — `UNAVAILABLE`. Так один «плохой» игрок не мешает остальным и не вызывает бесконечных повторов всего пакета. Паузу между такими обращениями задаёт `batch_pause_seconds`, общий темп не выше 20 запросов в секунду (R6).
- **Ключ недействителен** — коды 5, 27, 28: запись не меняется, `next_attempt_at = now + failure_retry_minutes`; в журнал CRITICAL один раз за процесс.
- **Прочие сбои** (сетевая ошибка, HTTP 5xx, коды 1, 6, 9, 10, 14, 29, 100 и любые другие в объекте `error`): запись не меняется, `next_attempt_at = now + failure_retry_minutes`; журнал — WARNING.

Очистка значений перед записью: имя и фамилия — убрать управляющие символы и краевые пробелы, обрезать до 64 символов; `photo_url` принимается только со схемой `https` и длиной не более 1024, иначе `NULL`. Если у игрока нет фото, ВК возвращает адрес-заглушку (`…/camera_50.png`, `…/camera_100.png`): такой адрес сохраняется как `NULL`, чтобы клиент показал собственный нейтральный кружок, а не серую камеру ВК. Адрес фото — непрозрачная строка без предположений о сроке жизни: обновление по `profiles.ttl_hours` обязательно (R7). Ключ и тела ответов в журнал не пишутся.

### 3.5. Форматирование дат

Месяцы — в родительном падеже из фиксированной таблицы в коде (локаль ОС не используется): январь→января, … , декабрь→декабря.

- **Игровая дата** (`formed`): $D = D_{epoch} + \lfloor N_{turn}\cdot R_{days}\rfloor$ (формула календаря `00_core`); текст `"{день} {месяц} {год} г."`, год без ведущих нулей (например, `"8 января 1 г."`, `"15 марта 1240 г."`). `key = created_turn`.
- **Реальная дата** (`joined`): $D_{msk} = \text{date}(created\_at\ \text{в зоне}\ tick\_timezone)$; текст `"{день} {месяц} {год}"` (например, `"13 октября 2026"`); ключ

$$key = D_{msk} - \text{1970-01-01}\quad(\text{в сутках})$$

Дата формируется на сервере, клиент не вычисляет даты из меток времени и не использует `Date` для игровых дат (год 1 в JS непредсказуем).

### 3.6. Формы ячеек по типу столбца

| Тип | Форма ячейки (JSON) |
| :-- | :-- |
| `index`, `integer`, `gauge` | целое число или `null` |
| `text` | строка или `null` |
| `date` | `{"text": str, "key": int}` или `null` |
| `datetime` | `{"date": "дд.мм.гггг", "time": "чч:мм", "key": int, "day": int, "mark": null \| "overdue"}` или `null`; пустая ячейка — все четыре поля `null`, `mark` сохраняется (просроченный этап без момента времени) |
| `action_text` | `{"text": str, "action": "<обработчик>:<аргумент>"}` или `null` |
| `person` | `{"name": str, "avatar_url": str \| null, "is_fallback": bool}` |
| `flag` | `{"color": "#RRGGBB", "image_url": str \| null}` |
| `nation` | `{"name": str, "color": "#RRGGBB", "flag_url": str \| null}` или `null` |

Форма точная: лишних ключей в ячейке нет, `cell_matches` проверяет набор ключей целиком. `date`/`time` ячейки `datetime` — текст в зоне `tz` (конструктор берёт зону параметром, источники передают `tick.tick_timezone`); `key` — Unix-секунды момента для сортировки; `day` — целые сутки от 1970-01-01 в той же зоне для фильтра `date_range`. Наивный `datetime` читается как UTC (соглашение хранения). `action` — строка вида `"order:12"`: клиент вызывает обработчик, зарегистрированный под именем до двоеточия, с остатком как аргументом (5.5).

### 3.7. Правила упорядочения, фильтров и поиска (выполняет клиент; Spec задаёт семантику)

- **Ключ сортировки:** `index`/`integer`/`gauge` — число; `text` — строка; `date` — `key`; `datetime` — `key`; `action_text` — `text`; `person` — `name`; `nation` — `name`. Пустое значение (`null`, а для `datetime` — и ячейка с `key = null`) всегда в конце, при любом направлении. Строки — сравнение русской локали без учёта регистра (`Intl.Collator('ru', {sensitivity: 'base'})`). Сортировка устойчива; равные ключи сохраняют порядок по умолчанию.
- **`text`:** «содержит»; регистр не важен; `ё` и `е` равны; краевые пробелы отбрасываются; пустое условие не фильтрует. Для `action_text` сравнивается `text`.
- **`number_range`:** границы включительно; пустая граница не ограничивает; применяется к числу или `date.key`.
- **`date_range`:** границы — календарные даты, переводятся в число суток от 1970-01-01 (арифметика по компонентам Y-M-D без часовых поясов) и сравниваются с `date.key`; для `datetime` — с `day`.
- **`presence`:** «есть» — ячейка не `null` (для `datetime` — ещё и `key` не `null`: пустая ячейка с отметкой считается «нет»); «нет» — наоборот.
- **`select_or_contains`:** фильтр столбца `nation` из двух независимых условий, объединённых по «И»: выпадающий список (точное совпадение `name` по нормализованной строке; «Все» — условие не задано) и поле «содержит» по правилу `text`. Опции списка — все государства, известные реестру: ячейки `name` таблицы `nations` (3.3); если она отсутствует в описании или не загрузилась — имена `nation`-ячеек видимых строк текущей таблицы. Пустые обе половины не фильтруют. На одном столбце `select_or_contains` не сочетается с `text` (поле «содержит» уже входит в него).
- **Общий поиск:** строка подходит, если условие `text` выполняется хотя бы для одного столбца с `searchable = true` (для `person` и `nation` — по `name`, для `action_text` — по `text`). Результаты фильтров, поиска и условий столбцов объединяются по «И». Счётчик «Показано N из M»: N — после фильтрации, M — `total` ответа.

Внутри — по одной подписанной группе на фильтруемый столбец в переносящейся сетке (`display: grid; grid-template-columns: repeat(auto-fill, minmax(200px, 1fr)); gap: 12px`): `text` — одно поле с подсказкой «содержит…»; `number_range` и `date_range` — два малых поля «от» и «до» рядом (подпись группы берётся из `filter_label`, например «Ход»); `presence` — трёхпозиционный выбор «Все / Есть / Нет»; `select_or_contains` — выпадающий список «Все / <государства>» и под ним поле «содержит…» (3.7). Открытость панели — часть состояния вкладки и сбрасывается при уходе с панели; блок таблицы хранит собственную прокрутку, открытие панели не создаёт горизонтальную полосу.

**Состояние:** сортировка, фильтры, поиск и открытость панели фильтров каждой вкладки хранятся в состоянии `PanelRegistry` и сохраняются при переключении вкладок; при уходе с панели («Назад») сбрасываются (Bible, 2.7). Открытие вкладки и «Обновить» запрашивают строки заново; описание таблиц запрашивается один раз при открытии панели.

**Ячейки:** `person` — круглая аватарка 24 px с запасным нейтральным кружком при `avatar_url = null` или ошибке загрузки, зазор 8 px и имя с обрезкой по ширине (полное название в `title`); `nation` — при заданном `flag_url` изображение флага (при ошибке загрузки — та же точка цвета), иначе точка цвета 10 px; зазор 8 px и название с обрезкой (полное в `title`) либо прочерк; `gauge` — число со знаком в фиксированные 36 px, выровненное вправо, и шкала на остаток ячейки с нулём в центре, отрицательная сторона слева, положительная справа (различие формой, не только цветом); `flag` — квадрат цвета или изображение; `date` — поле `text`; `datetime` — две строки: `date` над `time`, при `mark = "overdue"` текст в цвете ошибки (у пустой ячейки с отметкой вместо времени — подпись «срок вышел»); `action_text` — текст как кнопка-ссылка акцентного цвета; клик вызывает `runCellAction(action)`; `index`/`integer` — выровнены вправо; ячейки `date`, `datetime` и `integer` не переносятся (`white-space: nowrap`).

**Действия ячеек (`lib/cellActions.ts`).** Модуль-владелец данных регистрирует обработчик `registerCellAction(handler, fn)`; `runCellAction("handler:arg")` вызывает `fn(arg)`. Обработчик не зарегистрирован — клик ничего не делает. Реестр не знает о модулях-владельцах: строка `action` — весь контракт.

**Вход по хэшу (`lib/entryRequest.ts`, `AppShell.normalizeEntryHash`).** Хэш `#registry/order-<от 1 до 9 цифр>` — подсказка стартового экрана: `normalizeEntryHash` переписывает его на маршрут `#/registry` и сохраняет запрос `{tab: 'orders', action: 'order:<N>'}`. Больше девяти цифр или нецифровой номер — хэш игнорируется целиком. Панель получает запрос пропом `entryRequest`, выбирает вкладку `tab`, если такая таблица существует (нет — обычная первая вкладка), и после загрузки её строк вызывает `action` так же, как клик по ячейке `action_text`. Существующий `#registry` работает без изменений.

**Состояния:** загрузка — спиннер в блоке таблицы; ошибка — сообщение и «Повторить» (ранее показанные строки остаются); пустая таблица — `empty_text`; фильтр без результата — «Ничего не найдено» и «Сбросить». Тексты интерфейса (кнопки, подсказки) — константы клиента; тексты таблиц и столбцов — из ответа 5.1.

**События vk-bridge:** не используются.

## ПРИЛОЖЕНИЕ A: Контракт источников таблиц (для модулей-владельцев данных)

```python
# backend/src/modules/_03_registry/registry.py  (публичный API модуля)
from dataclasses import dataclass
from collections.abc import Awaitable, Callable
from sqlalchemy.ext.asyncio import AsyncSession

Cell = int | str | dict | None   # форма — Spec 3.6

@dataclass(frozen=True)
class RegistryRow:
    key: str                     # устойчивый в пределах ответа; не содержит vk_user_id и uuid игрока
    cells: dict[str, Cell]       # ключ значения -> ячейка

def register_table_source(
    key: str,
    provides: frozenset[str],
    load: Callable[[AsyncSession], Awaitable[list[RegistryRow]]],
) -> None: ...

# Конструкторы ячеек (backend/src/modules/_03_registry/cells.py):
# cell_date(text: str, key: int) -> dict
# cell_datetime(moment: datetime | None, tz: str, mark: str | None = None) -> dict
# cell_action_text(text: str, action: str) -> dict
# cell_person(name: str, avatar_url: str | None, is_fallback: bool) -> dict
# cell_flag(color: str, image_url: str | None) -> dict
# cell_nation(name: str, color: str, flag_url: str | None = None) -> dict
```

Источник читает только публичные функции своего модуля и не пишет в БД. Новый вид данных в существующей таблице: модуль-владелец добавляет ключ в `provides` своего источника (для встроенных `players` и `nations` — в `_03_registry`), затем столбец с этим `source` добавляется в конфиг.

**Конфиг:** реальный YAML валиден; отклоняются: неизвестный ключ, фильтр, недопустимый для типа (`select_or_contains` в том числе вне `nation`), `select_or_contains` вместе с `text` на одном столбце, `searchable` у `integer`, сортируемый `flag`, `gauge` без шкалы, шкала у `integer`, повтор идентификаторов, `default_sort` на несортируемый или отсутствующий столбец, `wake_interval_minutes` больше срока годности, шаблон без `{number}`, адрес `http://`. - **R1. CONFIRMED.** `users.get` допускает ключ сообщества, заголовок `Authorization: Bearer`; отдельного права не нужно, хватает существующего `VK_GROUP_TOKEN`. Новых переменных окружения нет.

- **R3. CONFIRMED.** `photo_50` — квадрат 50 px, `photo_100` — квадрат 100 px. Если фото нет, ВК отдаёт заглушку `https://vk.com/images/camera_50.png` (`camera_100.png`): модуль сохраняет `photo_url = NULL` (3.4).
- **R4. CONFIRMED с оговорками.** У удалённой или заблокированной страницы есть поле `deactivated` (`deleted` | `banned`), опциональные поля (фото) не приходят. **UNVERIFIED:** что лежит в `first_name`/`last_name` таких страниц (модуль их не применяет); пропускается ли несуществующий `id` или возвращается ошибка 113 (модуль обрабатывает оба исхода: 3.4). - **R5. CLARIFIED.** Для закрытых профилей документация не обещает ни выдачи, ни отказа; ошибка 30 («профиль приватный») обрабатывается как ошибка одного пользователя (3.4), частичный ответ сохраняется как есть.
