# 02_SYSTEM_SPECS / deploy — боевой сервер (пока он же staging)

## 1. Цель и границы

Один сервер в РФ, на который можно безболезненно накатывать обновления из GitHub и на котором автономно работает суточный ход (00:00 по Москве). Нужен для спринта VK-бота, Callback API и фоновых уведомлений. Пре-альфа: 20–50 тестировщиков, бюджет 500–1000 ₽/мес.

**Не входит в трек:** VK-бот и Callback API (только готовим сервер: публичный HTTPS, доступный `/api`), загрузка картинок флага/портрета (позже, в Docker-том), несколько серверов, Kubernetes, Redis, системы мониторинга, реестр образов.

## 2. Топология

```
Интернет ──443/80──► caddy ──/api/*──► backend:8000 ──► db:5432 (только внутренняя сеть)
                       │
                       └── всё остальное: собранный фронтенд (статика)
migrate — одноразовый контейнер: alembic upgrade head, затем выходит
```

Один домен: `/` — фронтенд, `/api/*` — бэкенд. CORS не нужен: фронтенд уже ходит на относительный `/api/v1`. Наружу открыты только порты 80/443 контейнера caddy.

## 3. Контейнеры

| Сервис | Основа | Правила |
|:--|:--|:--|
| `db` | `postgres:16` | именованный том `pgdata`; healthcheck `pg_isready`; порт наружу не публикуется; пароль из `.env` |
| `migrate` | образ backend | команда `alembic upgrade head`; `restart: "no"`; стартует после здоровой `db`; при ошибке стек не поднимается дальше |
| `backend` | образ backend | `uvicorn main:app --app-dir src`, **строго `--workers 1`**, без `--reload`; стартует только после успешного `migrate`; запуск не от root; `restart: unless-stopped`; healthcheck |
| `caddy` | multi-stage: node-сборка фронтенда → `caddy:2` | порты 80/443; тома `caddy_data` и `caddy_config` (в них хранятся сертификаты — не терять); автоматический HTTPS |

Общие правила: ротация логов Docker (`json-file`, `max-size` 10m, `max-file` 3); образы собираются из репозитория без `.env` (нужен `.dockerignore`); в образе есть пакет `tzdata` (игра живёт по `Europe/Moscow`).

**Раскладка внутри образа backend** повторяет репозиторий, потому что код ищет файлы относительно себя: `backend/src`, `backend/alembic` + `alembic.ini`, `configs/*.yaml`, а также **вся папка `data/map/`**: загрузчик карты при старте требует все шесть входных файлов (`manifest.json`, `geometry.json`, `ids.lock.json`, `boundary.yaml`, `overrides.yaml`, `source/map.svg`) и сверяет их контрольные суммы, поэтому исходный SVG обязан лежать в образе. Из образа исключаются только `data/map/preview/`, `tools/`, тесты, `.git`, `node_modules`. Корень данных можно переопределить переменной `MAP_DATA_DIR`. Проверяется запуском на чистой базе.

## 4. Конфигурация и секреты

- Все настройки — в одном `.env` в корне проекта на сервере (`/opt/goliath/.env`, права 600, владелец — пользователь деплоя). Подключается в compose через `env_file`. В образы и в репозиторий не попадает.
- В репозитории лежит только `.env.prod.example` с заглушками. Репозиторий публичный: в compose, Caddyfile и CI секретов нет.
- Переменные: `DATABASE_URL` (драйвер `postgresql+asyncpg`, хост `db`), `POSTGRES_PASSWORD`, `JWT_SECRET_KEY`, `VK_APP_ID`/`VK_APP_SECRET` (если код их требует), `ADMIN_VK_USER_IDS`, `ADMIN_ALLOW_RESET`, `APP_ENV=production`, `DOMAIN`, `ACME_EMAIL`. Переменные бота `02_bot` (`BOT_ENABLED`, `VK_GROUP_ID`, `VK_GROUP_TOKEN`, `VK_CALLBACK_SECRET`, `VK_CALLBACK_CONFIRMATION`) объявлены в `.env.prod.example` и заполняются при включении бота — см. §12.
- **Новые** для продакшена: `JWT_SECRET_KEY` и пароль БД (генерируются случайно, без специальных символов — пароль входит в адрес подключения). Секрет мини-аппа `VK_APP_SECRET` менять нельзя — он задан кабинетом ВК и совпадает с локальным.
- `DATABASE_URL_TEST` на сервере не задаётся никогда: тесты с пометкой `postgres` стирают схему базы.
- Единственный секрет в GitHub Secrets — SSH-ключ деплоя (появляется в последнем Issue трека).

## 5. Caddy

- Один сайт `{$DOMAIN}`: `handle /api/*` → `reverse_proxy backend:8000`; остальное — статика с запасным `index.html` (SPA); сжатие включено.
- Кэш: файлы с хэшем в имени (`/assets/*`) — `immutable`; `index.html` — без кэша. Геометрию карты бэкенд отдаёт со своими заголовками кэша.
- **Заголовки защиты от встраивания (`X-Frame-Options`, `frame-ancestors`) на первом этапе не ставим:** приложение живёт внутри окна ВК, неверный заголовок покажет игрокам белый экран. Добавим после проверки в живом ВК (бэклог).
- Выпуск сертификата требует, чтобы DNS-запись домена уже указывала на сервер, а порты 80/443 были открыты.

## 6. Проверки здоровья

- `GET /health` — как сейчас: «процесс жив». Используется Docker внутри контейнера.
- `GET /api/v1/health` — новый: «система работает». Проверяет связь с БД и то, что планировщик тиков жив (метка последнего прохода цикла не старше заданного порога). Ответ 200 или 503. Идёт через Caddy, поэтому проверяет всю цепочку: HTTPS → Caddy → backend → БД. Используется скриптом деплоя и внешним монитором.

## 7. Суточный ход на боевом сервере

Планировщик остаётся внутри процесса FastAPI. Инварианты:

1. **Один воркер.** Зафиксирован в Dockerfile и в runbook.
2. **Блокировка хода в PostgreSQL:** в начале транзакции хода берётся `pg_try_advisory_xact_lock(<константа>)`. Если блокировка занята — ход тихо пропускается (это не ошибка и не запись `FAILED`). Блокировка берётся **до** создания строки `RUNNING` в `tick_log`, иначе проигравший оставит в журнале «вечный RUNNING». Защищает от двух экземпляров приложения во время деплоя и от наложения ручного хода админа на автоматический.
3. **Перепроверка расписания:** после блокировки `game_clock` читается под `SELECT … FOR UPDATE`; если `next_tick_at` ещё в будущем — ход пропускается. Это правило действует только для автоматического пути; ручной запуск админом перепроверку не использует (но блокировку использует).
4. **SQLite:** блокировка PG-специфична, на SQLite пропускается (тесты в одном процессе).
5. **Живучесть планировщика:** временная ошибка (БД недоступна, контейнер БД перезапускается) не должна убивать цикл. Цикл ловит ошибку, логирует, ждёт `retry_delay_seconds` и продолжает; каждый проход обновляет «метку жизни» для `/api/v1/health`.
6. **Свежая база:** на пустой базе после `alembic upgrade head` строка `game_clock (id=1)` обязана существовать, иначе планировщик не стартует. Проверяется приёмочным запуском в Issue DEP-1.
7. **Тесты:** двойной запуск (два одновременных вызова → ровно один ход), занятая блокировка, будущий `next_tick_at`, живучесть цикла при ошибке БД — на реальном PostgreSQL (маркер `postgres`), без моков.

## 8. Предохранители боевого режима

- `ADMIN_ALLOW_RESET` (по умолчанию `false`): при `false` эндпоинт сброса мира отвечает 403 `RESET_DISABLED`. На пре-альфе владелец включает флаг в `.env` и перезапускает backend, когда нужен сброс; перед настоящим запуском оставляет выключенным. Ручной запуск хода остаётся разрешённым админам.
- `ADMIN_VK_USER_IDS` — минимальный список (только владелец проекта).
- При `APP_ENV=production` приложение отказывается стартовать, если `JWT_SECRET_KEY` короче 32 символов или совпадает с известной dev-заглушкой, а также если не задан `DATABASE_URL` с хостом, отличным от `localhost`.

## 9. Деплой, откат, бэкапы

**`deploy.sh`** (запускается на сервере под пользователем деплоя): проверки (нет незакоммиченных правок, `.env` есть и с правами 600, не окно 23:55–00:10 по Москве — иначе нужен флаг `--force`) → бэкап перед деплоем (хранятся последние 7) → `git fetch` и переход на нужный тег или `main` → сборка образов → остановка backend → `migrate` → запуск backend и caddy → ожидание здоровья → проверка `https://$DOMAIN/api/v1/health`. При сбое скрипт печатает инструкцию отката и не пытается откатывать сам.

**Откат:** код — вернуть предыдущий тег и пересобрать. База — миграции только вперёд; откат базы делается восстановлением из бэкапа перед деплоем. Поэтому миграции пишутся совместимыми (добавление, а не удаление/переименование), пока это возможно.

**Бэкап (`backup.sh`):** ежедневный `pg_dump` из cron хоста около 00:30 по Москве (`CRON_TZ=Europe/Moscow`, сам хост остаётся в UTC); хранение 14 дней; **копия вне сервера обязательна** (хранилище S3-совместимое или иное — выбирается в Issue DEP-5; дампы перед отправкой шифруются, в них идентификаторы игроков ВК); раздел данных Docker-тома с загрузками (позже) входит в бэкап. **Проверка восстановления обязательна:** скрипт `restore_check.sh` поднимает последний дамп во временную БД и сверяет счётчики строк; полная репетиция восстановления выполняется один раз перед открытием для тестировщиков и затем по расписанию в runbook.

**Отклонения, зафиксированные при реализации (DEP-5):**

- cron использует фиксированное время UTC (`30 21 * * *` = 00:30 МСК) вместо `CRON_TZ`: не все реализации cron поддерживают `CRON_TZ`; владелец сверяет `timedatectl` и при ином поясе пересчитывает час (инструкция в `deploy/cron.example`).
- Бэкапы `predeploy` делаются только локально (флаг `--local-only`), внешняя копия — только у ежедневных.
- Внешняя копия: шифрование `age` публичным ключом (приватный хранится офлайн у владельца), отправка через `rclone` в S3-совместимое хранилище (`BACKUP_AGE_RECIPIENT`/`BACKUP_RCLONE_REMOTE` в `~/.config/goliath/backup.env`).
- Локальные дампы намеренно не шифруются: лежат только на сервере (права 600, папка 700), что позволяет `restore_check.sh` проверять восстановление без приватного ключа.

## 10. Минимальная защита сервера

Вход только по SSH-ключам (пароль и root-вход отключены), файрвол: открыты 22/80/443, работа от отдельного пользователя деплоя, автоматические обновления безопасности, swap 2 ГБ, ротация логов Docker. Автодеплой (последний Issue): только по тегу релиза или кнопкой, выполняется в GitHub Environment `production` с подтверждением владельцем; ключ ограничен командой деплоя; workflow деплоя никогда не запускается от `pull_request`.

## 11. Известные риски (фиксируются, не блокируют)

- Docker Hub с российских серверов по публикациям 2024 года блокировался или работал нестабильно; актуальное состояние проверяем при выборе провайдера (зеркало у провайдера или в настройках Docker). Запасной путь — собирать образы в GitHub Actions (бэклог).
- Один адрес приложения в кабинете ВК: тестировщикам нужен боевой адрес, владельцу — `localhost` для разработки. Решается на шаге настройки кабинета (отдельный адрес для разработки, если ВК его даёт, иначе второе приложение).
- Простой, но пока без ограничения частоты запросов публичный `/api/v1/auth/vk` (бэклог).

## 12. Модуль 02_bot (VK-бот) — v0.1.1

Модуль бота сообщества выпущен версией **v0.1.1** и выключен по умолчанию (`BOT_ENABLED` не задан — режим `OFF`, сервер ничем не отличается от прежнего). Спецификация и роадмап: `docs/02_SYSTEM_SPECS/02_bot.md`, `docs/03_ROADMAP/02_bot.md`; порядок включения для владельца — `docs/deploy_runbook.md`, раздел 13.

Контракт включения:

- Пять переменных в `.env` + выключатель `BOT_ENABLED=true`; при `BOT_ENABLED` без полного набора `VK_*` режим `MISCONFIGURED` — сервер стартует, бот молчит, лог называет недостающие переменные (только имена). `VK_APP_ID` опционален: без него нет кнопки «Создать государство».
- Callback-адрес для кабинета ВК: `https://<домен>/api/v1/bot/callback`. Публичные эндпоинты игрока: `GET /api/v1/bot/status`, `POST /api/v1/bot/consent/refresh`.
- Включение двухэтапное: сначала с `consent.required_for_registration: false` (значение релиза), после приёмки в настоящем ВК — `true` (одна строка конфига + деплой, трек «А»).
