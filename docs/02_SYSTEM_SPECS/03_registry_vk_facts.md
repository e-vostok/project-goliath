# 02_SYSTEM_SPECS / 03_registry_vk_facts — Проверка фактов о VK API (задача REG-0)

> Исполнитель: IDE Execution Agent (Devin). Дата проверки: 2026-10-13.
> Источники: только первоисточники — `dev.vk.com` (официальная документация ВК) и репозитории `github.com/VKCOM/*` (`vk-api-schema`). Реальные вызовы VK API не выполнялись (DENYLIST задания).
> Каждый пункт R1–R8 соответствует строке Приложения V Spec `docs/02_SYSTEM_SPECS/03_registry.md`.

## Сводка готовых значений для Spec и конфига

- `profiles.photo_field` = `photo_50` — квадратная аватарка 50 px (запасной вариант `photo_100`, 100 px). При отсутствии фото ВК возвращает заглушку `https://vk.com/images/camera_50.png` / `camera_100.png` (R3).
- `profiles.batch_size`: потолок метода — **1000** `user_ids` за вызов (`maxItems: 1000` в официальной JSON-схеме); текущий диапазон `1…1000` и старт `100` корректны (R2).
- Правило разбора: если у элемента есть поле `deactivated` (`deleted` или `banned`) либо запрошенный `id` отсутствует в массиве `response` → `status = UNAVAILABLE`, имя и фото не перезаписывать; опциональные поля у `deactivated`-элементов не приходят вообще (R4).
- `users.get` вызывается ключом сообщества `VK_GROUP_TOKEN` заголовком `Authorization: Bearer`; отдельного права для метода не требуется — достаточно существующего ключа (R1).
- Лимит частоты ключа сообщества — **20 запросов/с** (факт V5 подтверждён повторно); `profiles.api_base_url = https://api.vk.ru/method`, `profiles.api_version = 5.199` (V12, V13) остаются в силе (R6).

### R1 — `users.get` с ключом доступа сообщества (`Authorization: Bearer`); нужные права

- Status: CONFIRMED
- Fact: На странице метода `users.get` в разделе допустимых ключей перечислены все три типа: «ключ доступа пользователя», «ключ доступа сообщества», «сервисный ключ доступа». Официальная JSON-схема фиксирует то же: `"access_token_type": ["user", "group", "service"]`. Ключ передаётся заголовком `Authorization: Bearer <КЛЮЧ_ДОСТУПА>` (V3). Отдельное право доступа для `users.get` нигде не названо: перечень прав ключа сообщества — `stories`, `photos`, `app_widgets`, `messages`, `docs`, `manage` — не содержит права на чтение профилей, то есть метод доступен любому ключу сообщества, включая существующий `VK_GROUP_TOKEN` с правом `messages`.
- Source: https://dev.vk.com/ru/method/users.get («Для вызова метода можно использовать»), https://dev.vk.com/ru/reference/json-schema (фрагмент схемы `users.get`), https://github.com/VKCOM/vk-api-schema (`users/methods.json`), https://dev.vk.com/ru/api/privacy («Ключ доступа сообщества» — список прав), https://dev.vk.com/ru/api/api-requests («Заголовки»)
- Spec impact: п. 3.4 — подтверждено без правок: `POST {profiles.api_base_url}/users.get` с заголовком `Authorization: Bearer <VK_GROUP_TOKEN>`; новых прав и нового ключа не нужно.

### R2 — Максимальное число `user_ids` за вызов

- Status: CONFIRMED
- Fact: Параметр `user_ids` — массив идентификаторов или `screen_name`, передаваемый строкой через запятую. В официальной JSON-схеме VK API для `users.get` задано `"maxItems": 1000` — до 1000 идентификаторов за одно обращение. Та же цифра приведена на странице dev.vk.com «JSON-схема» в разборе метода `users.get`.
- Source: https://dev.vk.com/ru/reference/json-schema (пример схемы `users.get`, `maxItems: 1000`), https://github.com/VKCOM/vk-api-schema (`users/methods.json`, параметр `user_ids`)
- Spec impact: п. 4.3 — диапазон `profiles.batch_size` `1…1000` и старт `100` подтверждены; правки не требуются.

### R3 — Поля малой аватарки и размеры в пикселях

- Status: CONFIRMED
- Fact: Параметр `fields` принимает `photo_50`, `photo_100`, `photo_200`, `photo_200_orig`, `photo_400_orig`, `photo_id`, `photo_max`, `photo_max_orig` (и прочие профильные поля). По справочнику объекта `user`: `photo_50` — URL **квадратной** фотографии шириной 50 px; `photo_100` — квадратной, 100 px; `photo_200` — квадратной, 200 px; `photo_max` — квадратной с максимальной доступной шириной (100 или 200 px); `photo_200_orig`/`photo_400_orig` — НЕ квадратные (исходные пропорции). Если у пользователя нет фотографии, возвращается заглушка `https://vk.com/images/camera_50.png` / `camera_100.png` / `camera_200.png` / `camera_400.png` соответственно размеру.
- Source: https://dev.vk.com/ru/method/users.get (список `fields`), https://dev.vk.com/ru/reference/objects/user (`photo_50`, `photo_100`, `photo_200`, `photo_max`, заглушки `camera_*.png`)
- Spec impact: п. 4.3 — `profiles.photo_field = photo_50` подтверждено; для ячейки 24 px хватает `photo_50`, вариант `photo_100` в списке допустимых значений конфига корректен. Полезное уточнение для реализации: поле содержит URL заглушки, когда у игрока нет аватарки — отдельной обработки «нет фото» не требуется (или заглушку можно распознавать по имени `camera_*.png`).

### R4 — Удалённая/заблокированная страница и несуществующий идентификатор

- Status: CONFIRMED (с оговорками UNVERIFIED)
- Fact: Справочник объекта `user`: поле `deactivated` «возвращается, если страница пользователя удалена или заблокирована, содержит значение `deleted` или `banned`. В этом случае опциональные поля не возвращаются» — то есть `photo_50` и другие поля из `fields` у такого элемента отсутствуют. Базовые поля `id`, `first_name`, `last_name` по JSON-схеме обязательны (`required`). Точное содержимое `first_name`/`last_name` у удалённого или заблокированного пользователя в документации не описано — **UNVERIFIED** (полагаться на текст имени нельзя). В схеме `users_user_min` есть также поле `hidden` (`integer`, «Returns if a profile is hidden») — признак скрытой страницы. Поведение для несуществующего `id` (элемент опускается из `response` или возвращается ошибка) на dev.vk.com прямо не описано — **UNVERIFIED**; в общем списке ошибок есть код 113 «Неверный идентификатор пользователя» (рекомендация — `utils.resolveScreenName`), применимость его к несуществующему числовому `id` не зафиксирована.
- Source: https://dev.vk.com/ru/reference/objects/user (`deactivated`), https://github.com/VKCOM/vk-api-schema (`users/objects.json`, `users_user_min`: `deactivated`, `hidden`, `required`-поля), https://dev.vk.com/ru/reference/errors (код 113)
- Spec impact: п. 3.4 — правило разбора подтверждено и достаточно: признак `deactivated` в элементе ИЛИ отсутствие запрошенного `id` в массиве `response` → `status = UNAVAILABLE`, поля имени/фото не применять. Дополнительно безопасно считать `hidden = 1` эквивалентом `UNAVAILABLE` (необязательная правка). Ошибка 113 — добавить в таблицу реакций как WARNING (сбой запроса, повтор по `failure_retry_minutes`).

### R5 — Закрытые профили (`is_closed`, `can_access_closed`)

- Status: CLARIFIED
- Fact: В объекте `user` задокументированы поля `is_closed` («скрыт ли профиль настройками приватности») и `can_access_closed` («может ли текущий пользователь видеть профиль при `is_closed = 1`, например он есть в друзьях»). В общем списке ошибок существует код 30 «Профиль является приватным — информация, запрашиваемая о профиле, недоступна с используемым ключом доступа». Явного утверждения, что для закрытого профиля ключ сообщества получает/не получает `first_name`, `last_name` и `photo_50`, на dev.vk.com нет — **UNVERIFIED**; базовые поля при этом документально не зависят от настроек приватности (оговорка справочника касается только полей «о текущем пользователе», требующих ключ пользователя). Для ключа сообщества понятие «текущий пользователь» отсутствует, поэтому `can_access_closed` следует ожидать равным `false`.
- Source: https://dev.vk.com/ru/reference/objects/user (`is_closed`, `can_access_closed`, оговорка про ключ пользователя), https://dev.vk.com/ru/reference/errors (код 30)
- Spec impact: п. 3.4 — правок не требуется: модуль сохраняет то, что вернул ВК; если у закрытого профиля придёт имя без фото или наоборот — ячейка корректно покажет частичный результат, а при полном отказе (ошибка 30/нет полей) сработает ветка `UNAVAILABLE` и запасной вид. Добавить ошибку 30 в таблицу реакций (WARNING → повтор по `failure_retry_minutes`), чтобы она не трактовалась как сбой авторизации.

### R6 — Коды ошибок `users.get` и лимит частоты ключа сообщества

- Status: CONFIRMED
- Fact: На странице `users.get` метод-специфичных кодов нет — действуют только «общие ошибки» справочника. Релевантные модулю: 1 и 10 (внутренние сбои — повтор), 5 («Авторизация пользователя не удалась»), 27 и 28 (недействительный ключ сообщества/приложения → CRITICAL один раз за процесс, как в Spec), 6 («Слишком много запросов в секунду» — превышение частоты), 9 (флуд-контроль), 14 (требуется капча), 29 (количественный лимит на вызов метода — точные числа ВК не раскрывает), 30 (приватный профиль), 100 (неверный параметр), 113 (неверный идентификатор пользователя). Лимит частоты для ключа доступа сообщества — **20 запросов в секунду** — подтверждён таблицей «Ограничения» страницы «Формат запросов» (факт V5 распространяется и на `users.get`).
- Source: https://dev.vk.com/ru/method/users.get («Коды ошибок»), https://dev.vk.com/ru/reference/errors, https://dev.vk.com/ru/api/api-requests («Ограничения»)
- Spec impact: п. 3.4 — классификация ошибок подтверждена: 5, 27, 28 → CRITICAL; 6, 9, 14, 29, 30, 100, 113 и прочие → WARNING, повтор по `failure_retry_minutes`. Скорость обхода игроков: `batch_size`/`batch_pause_seconds` должны держать темп ≤ 20 запросов/с (при старте 1 обращение/`batch_pause_seconds = 1` с запасом под этим пределом).

### R7 — Стабильность URL фото, хотлинк и домены для CSP

- Status: UNVERIFIED (с документированными фрагментами)
- Fact: Документация не заявляет ни срока жизни, ни подписи, ни истечения URL аватарок (`photo_50`/`photo_100` — просто строка-URL), и не описывает ограничений хотлинка или заголовка `Referer` при показе изображения на странице внутри iframe мини-приложения. Документированные домены-источники: заглушки — `https://vk.com/images/camera_*.png` (справочник `user`); реальные фото в официальных примерах отдаются с CDN-хостов вида `sun9-west.userapi.com`, `sun9-north.userapi.com`, `sun9-east.userapi.com` (пример ответа `photos.saveOwnerPhoto`) и `pp.vk.me` (пример «Формат описания размеров фотографии»). Единого документированного списка доменов для CSP нет.
- Source: https://dev.vk.com/ru/reference/objects/user (`photo_50`, `photo_100`, заглушки), https://dev.vk.com/ru/method/photos.saveOwnerPhoto (пример ответа с `sun9-*.userapi.com`), https://dev.vk.com/ru/reference/objects/photo-sizes (пример с `pp.vk.me`)
- Spec impact: п. 3.4 и 5.5 — закладываться на «вечный» URL нельзя: `photo_url` хранится как непрозрачная строка и обновляется по `ttl_hours` (24 ч), что уже защищает от любой смены адреса. Для будущего CSP фронтенда безопасный документированный перечень: `img-src https://*.userapi.com https://pp.vk.me https://vk.com` (перечень уточняется по факту при настройке CSP — отдельной правкой). При недоступности сохранённого URL клиент показывает запасной нейтральный кружок — поведение Spec уже описано.

### R8 — Правила платформы о показе имени и фото другим пользователям приложения

- Status: CONFIRMED (прямого запрета нет; есть обязанности по обработке данных)
- Fact: Правила платформы запрещают: собирать и хранить данные пользователей (включая User ID) «в целях, не связанных с функционированием Приложения» — данные должны использоваться «только в контексте приложения» (п. 2.1); передавать данные, полученные через API, сторонним сервисам (п. 2.2); использовать пользовательские данные в рекламных объявлениях (п. 2.3); перепродажу/скоринг (п. 2.4). Показ имени и аватарки игрока другим пользователям внутри приложения правилами не запрещён — это использование «в контексте приложения» (стандартные таблицы/рейтинги). Обязанности по правилам размещения VK Mini Apps: пользователь должен быть уведомлен о целях обработки и дать согласие (п. 1.1.2), в Панели управления обязательны пользовательское соглашение и политика конфиденциальности (п. 1.1.4), по требованию пользователя данные удаляются (п. 1.1.10).
- Source: https://dev.vk.com/ru/rules/2024-march-1 (пп. 2.1–2.4), https://dev.vk.com/ru/mini-apps-rules (пп. 1.1.2, 1.1.4, 1.1.5, 1.1.8, 1.1.10)
- Spec impact: дизайн подтверждён: хранение `first_name`/`last_name`/`photo_url` в `registry_vk_profiles` и показ их в таблице игроков — обработка «в контексте приложения», отдельное согласие каждого показываемого игрока через ВК не требуется. Для чек-листа Project Owner: в пользовательском соглашении и политике конфиденциальности (Панель управления приложения) зафиксировать показ имени и аватарки ВК в реестре и срок хранения; предусмотреть удаление профиля по требованию игрока (ручная операция — заявка через сообщество). INV-R2 (не отдавать `vk_user_id` клиенту) уже соответствует п. 2.1–2.2.

## Профиль игрока для подэкрана (0.10.0)

> Исследование единицы 2 версии 0.10.0. Исполнитель: IDE Execution Agent (Devin). Дата: 2026-10-23. ВК не вызывался; отмечено «проверено по коду» — или «не проверено», если ответ зависит от поведения ВК.

**Откуда берутся имя и аватарка; когда создаётся строка; сроки и повторы.** Таблица `registry_vk_profiles` (`models.py`, проверено по коду): `player_id` (первичный ключ, FK → `players.id` с CASCADE), `status` (`PENDING` / `OK` / `UNAVAILABLE`), `first_name` (64), `last_name` (64), `photo_url` (1024), `fetched_at`, `next_attempt_at`. Строка создаётся **не при входе**, а фоновой задачей (`profile_worker.run_cycle`, проверено по коду): каждый проход заводит `PENDING` со сроком «сейчас» на каждого игрока из `PlayerService.list_for_registry` без строки. Сроки (проверено по коду и `configs/03_registry.yaml`): `ttl_hours` = 24 ч — после любого ответа по игроку `fetched_at = now`, `next_attempt_at = now + 24 ч`; пакетный сбой (транспорт, HTTP 5xx, прочие ошибки) — `next_attempt_at = now + failure_retry_minutes` (15 мин), имя, фото и статус не трогаются; ответ `UNAVAILABLE` статус меняет, а прежние удачные имя и фото сохраняются (поля не перезаписываются). Период задачи — `wake_interval_minutes` = 30 мин плюс немедленный будильник от источника таблицы игроков, когда виден игрок без строки или с наступившим `next_attempt_at`. При `profiles.enabled = false` или пустом `VK_GROUP_TOKEN` задача выключена (`OFF` / `NO_TOKEN`) и таблицы показывают запасные имена (проверено по коду).

**Игрок без кэшированного профиля и без государства** (проверено по коду: `sources.py`, `cells.py`, `PersonCell.tsx`). Ячейка `person` — `{name, avatar_url, is_fallback}`: имя собирается из `first_name` + `last_name` при любом статусе строки, аватарка — только при `status = OK`. Пустое имя (нет строки или ВК ничего не отдал) → запасное `Игрок №{number}` из конфига и `is_fallback: true`; аватарки нет — круглый значок-заглушка с иконкой. У `UNAVAILABLE`-строки с прежним именем таблица показывает последнее удачное имя без аватарки. Игрок без государства: ячейка `nation` пустая, в подсказке — «нет государства», при сортировке по государству такие строки в конце (пустые значения всегда последние).

**Гарантия строки и скорость появления имени.** Каждый вошедший игрок получает строку лениво — на ближайшем проходе задачи (проверено по коду; строки `players` не удаляются, поэтому обход полный). Худший случай — `wake_interval_minutes` (30 мин) после входа; обычно раньше: открытие вкладки «Игроки» будит задачу, а свежая `PENDING`-строка со сроком «сейчас» попадает в тот же цикл — имя и аватарка появляются уже в нём, если ВК ответил (сам ответ ВК — не проверено). Пакет — до `batch_size` = 100 игроков за обращение, пауза 1 с между пакетами.

**Срок жизни URL аватарки.** Документация ВК срок жизни и ограничения URL не называет (R7 — не проверено, UNVERIFIED): на «вечный» адрес закладываться нельзя, поэтому копия обновляется каждые 24 ч. Если сохранённый URL умрёт на CDN между обновлениями, клиент показывает нейтральный круглый значок с иконкой (`onError` в `PersonCell`, проверено по коду): имя остаётся, таблица не ломается.

**Что уже публично в таблице «Игроки»** (проверено по коду: `configs/03_registry.yaml`, `sources.py`): №; игрок (имя, аватарка, `is_fallback`); дата регистрации; уровень (столбец-заглушка — у всех 1); судейский рейтинг (шкала −100…100, заглушка — у всех 0); государство (краткое название или полное для дорелизных, цвет, флаг, `nation_id` в ячейке). Подсказка у игрока показывает имя, дату регистрации, уровень, рейтинг, государство — из ячеек строки, без запроса. `vk_user_id` и uuid игрока клиенту не отдаются (INV-R2; ключ строки — `p<number>`). Подэкран «Игрок» ничего нового о чужом игроке не раскрывает — весь состав уже есть в таблице и подсказке; маршрута публичных сведений об игроке пока нет (существуют только `GET /players/me` и админ-маршруты — проверено по коду).

**Открытые вопросы для Lead AI:**
- Адресация подэкрана: ключ строки — `p<number>` (порядковый номер в сортировке `created_at, id`, детерминирован, пока игроки не удаляются, но не хранится в базе). Подходит ли ссылка вида `#registry/player-N` и маршрут по этому номеру — решение за Lead AI.
- Подэкран для `UNAVAILABLE`-игрока: показывать последнее удачное имя (как таблица) или запасное «Игрок №N» — решить при проектировании.
- Закрытый профиль может вернуть часть полей (R5 — не проверено): подэкрану достаточно показывать то, что есть в кэше, без отдельной логики.
