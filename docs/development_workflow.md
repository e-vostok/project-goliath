# develoment_workflow.md

> **Статус документа:** Production Standard  
> **Архитектурный паттерн:** Модульные вертикальные срезы (Modular Vertical Slices).  
> **Стратегия контекста:** Изолированная сессия чата (New Chat) под каждый Модуль.  
> **Интеграция:** Lead AI подключен к GitHub-репозиторию проекта на чтение.

---

## 1. Доменная концепция: Что такое «Модуль»

В архитектуре проекта **Модуль (Gameplay Module / Bounded Context)** — это автономная, функционально завершенная игровая подсистема, которая владеет изолированным куском игрового состояния и имеет собственную фазу расчета в пошаговом цикле симуляции.

Модуль — это **не** один файл и **не** абстрактная папка с кодом.  
Модуль — это **сквозной вертикальный срез (Vertical Slice)**, пронизывающий весь проект под единым системным именем (`[module_slug]`):

```text
project/
├── 01_GAME_BIBLE/[module_slug].md     ◄── Смысловой слой: правила и концепт (Что? Зачем?) ("Библия-файлы модулей")
├── 02_SYSTEM_SPECS/[module_slug].md   ◄── Архитектурный слой: сущности, инварианты, LaTeX-формулы ("Спек-файлы модулей")
├── configs/[module_slug].yaml         ◄── Балансовый слой: живые числа, читаемые движком ("Конфиг-файлы модулей")
└── 03_ROADMAP/[module_slug].md        ◄── Исполнительный слой: упорядоченный список Issues для IDE Agent ("Роадмап-файлы модулей")
```

### Архитектурные цели модульности:
1. **Токеноэффективность (Zero Context Saturation):** Под каждый модуль открывается **отдельная сессия чата с Lead AI**. Ни Lead AI, ни IDE Agent никогда не перегружают контекстное окно всей кодовой базой — они работают строго в границах активного модуля и его прямых зависимостей.
2. **Контроль радиуса взрыва (Blast Radius):** Ошибка агента при реализации или рефакторинге одного модуля физически не может повредить данные или логику других подсистем.
3. **Безопасный баланс:** Все числовые параметры вынесены в `configs/[module_slug].yaml`. Владелец проекта может менять баланс на ходу без коммитов в логику бэкенда.

---

### Онтологические критерии: Что является модулем, а что нет

При проектировании Lead AI руководствуется правилом: механика объявляется новым модулем ТОЛЬКО если она удовлетворяет **ВСЕМ четырем критериям одновременно**:

| Критерий | Что проверяется | Если «НЕТ» |
| :--- | :--- | :--- |
| **1. Суверенность данных (State Ownership)** | Есть ли у механики свои уникальные таблицы/поля в БД, которые не принадлежат другим системам? | Механика встраивается в существующий модуль, владеющий этими данными. |
| **2. Фаза в Серверном Тике (Tick Phase)** | Имеет ли механика собственный шаг расчета при смене хода (начисление, списание, прирост, смена статуса)? | Если механика пассивна/статична — это свойство или справочник другого модуля. |
| **3. Изоляция баланса (Config Isolation)** | Можно ли вынести все числовые параметры механики в отдельный `configs/[module_slug].yaml`? | Если параметры неотделимы от чужого конфига — механика относится к тому модулю. |
| **4. Вес подсистемы (Scope Sizing)** | Раскладывается ли реализация механики на бэкенде в диапазон от **3 до 6 атомарных Issues**? | Если 1–2 задачи — это фича внутри модуля. Если > 7 задач — концепт перегружен и требует дробления. |

#### Исключение: Базовый модуль ядра (`00_core`)
Модуль `00_core` является корневым инвариантом системы. Он описывает сущность учетной записи игрока, привязку государства к карте, сам цикл пошагового таймера (Тика) и глобальные системные типы данных. Все остальные модули по умолчанию ссылаются на `00_core` в блоке зависимостей (`dependencies`).

## 2. Ролевая модель и организация контекста

```
┌─────────────────────────────────────────────────────────────┐
│                    Project Owner (Человек)                  │
│            Видение, баланс (configs/*.yaml), PR             │
└──────────────┬───────────────────────────────▲──────────────┘
               │                               │
    Сырые идеи │                 Номер PR /    │ Утверждение PR
    и ссылки   ▼                 Имя ветки     │ и отчет тестов
┌──────────────────────────────┐ ┌─────────────┴──────────────┐
│  Lead AI                     │ │  IDE Agent                 │
│  [Отдельный чат на модуль]   │ │  Код, тесты, ветки Git,    │
│  Чтение GitHub репозитория   │ │  чтение configs/*.yaml     │
└──────────────┬───────────────┘ └─────────────▲──────────────┘
               │                               │
               └────► [ GitHub Репозиторий ] ──┘
```

1. **Project Owner (Человек):**
   * Открывает новую сессию чата под каждый новый модуль.
   * Формулирует идеи своими словами, утверждает спецификации.
   * Напрямую редактирует баланс в `configs/[module].yaml`.
   * Передает ТЗ агенту IDE.
   * Утверждает Pull Request'ы в репозиторий.

2. **Lead Systems Architect (Lead AI):**
   * *Контекст:* Подключен к GitHub-репозиторию проекта на чтение. Работает в изолированном чате конкретного модуля.
   * *Функции:* Напрямую исследует структуру файлов и код репозитория через GitHub, проектирует правила и спецификации, декомпозирует задачи, пошагово пишет ТЗ на английском языке и инспектирует Pull Request'ы.
   * *Ограничение:* Не пишет рабочий код реализации напрямую в ветки (не имеет локального рантайма и терминала для прогона тестов).

3. **IDE Execution Agent:**
   * *Контекст:* Работает непосредственно в локальном репозитории проекта.
   * *Функции:* Реализует Issues строго по одному ТЗ за раз, пишет код и интеграционные тесты, коммитит, пушит ветку и открывает Pull Request.

   ### Двухконтурная модель чатов с Lead AI:
**A. Мастер-чат («Обсерватория проекта» / Постоянная сессия):**
   * *Назначение:* Постоянно открытый стратегический диалог для взгляда на проект «с высоты птичьего полета».
   * *Функции:* По команде сканирует репозиторий, анализирует общую картину (что уже написано в коде, какие Issues закрыты в `03_ROADMAP/`, где накопился технический долг), оценивает текущую стадию проекта и рекомендует, за какой модуль логичнее браться следующим. В этом чате не пишутся детальные ТЗ для агента — здесь ведется только высокоуровневый надзор и архитектурное консультирование.

**B. Модульные чаты (Изолированные рабочие сессии):**
   * *Назначение:* Временный чат, открываемый строго под разработку одного конкретного модуля.
   * *Функции:* Проведение модуля по 4-шаговому пайплайну. Закрывается после релиза модуля.

## 3. Единое версионирование проекта (Semantic Versioning)

Версионируется **только проект целиком** единой сквозной версией. 

Версия проекта фиксируется в корневом файле `CHANGELOG.md`, в метаданных проекта (например, `package.json`) и через Git-теги репозитория (`vX.Y.Z`).

Формат: **`MAJOR.MINOR.PATCH`**

| Уровень | Обозначение | Когда применяется | Пайплайн обновления |
| :--- | :--- | :--- | :--- |
| **PATCH** | `x.x.+1` *(0.1.0 → 0.1.1)* | Изменение чисел в `configs/*.yaml`, правка опечатки в формуле, багфикс | Быстрый: правка конфига или фикс бага в кодовой базе |
| **MINOR** | `x.+1.0` *(0.1.5 → 0.2.0)* | Полное завершение и мерж всех Issues одного модуля из `03_ROADMAP/` | Плановый: закрытие модуля, бамп версии, закрытие чата модуля |
| **MAJOR** | `+1.0.0` *(0.9.0 → 1.0.0)* | Релиз ключевого этапа (MVP), кардинальная смена ядра симуляции | Аудит: полный аудит проекта перед релизом |

## 4. Сквозной пайплайн разработки модуля (4 шага)

> **Правило сессий:** Для разработки каждого нового модуля Project Owner открывает **новый чат** с подключенным GitHub-репозиторием.

```
[Новый чат: Инициализация] ──► [Шаг 1: BIBLE] ──► [Шаг 2: SPECS & configs] ──► [Шаг 3: ROADMAP] ──► [Шаг 4: Цикл ТЗ ⇄ PR через IDE]
```

### ШАГ 0. Инициализация сессии модуля
1. Project Owner создает новый диалог (в рамках проекта с подключенным GitHub-репозиторием).
2. Отправляет **ПРОМПТ 0 (Kickoff)** с указанием имени модуля и ссылками на зависимости. Lead AI синхронизируется с кодовой базой.

### ШАГ 1. Формализация модуля в `01_GAME_BIBLE/[module].md`
1. Project Owner описывает концепт механики своими словами через **ПРОМПТ 1**.
2. Claude анализирует идею по 4 критериям (Данные, Тик, Конфиг, Объем):
   * Если идея встраивается в существующий модуль — формирует текст обновления с указанием места в файле Библии модуля из папки 01_GAME_BIBLE, куда следует вставить новый фрагмент текста.
   * Если создается новый модуль — фиксирует границы (In-Scope / Out-of-Scope), зависимости и генерирует `01_GAME_BIBLE/[module].md`.
3. Project Owner сохраняет новую версию файла Библии модуля или файл Библии нового модуля в репозиторий.

### ШАГ 2. Генерация спецификации и конфигурации
1. В **ПРОМПТ 2** передается утвержденный текст Библии модуля.
2. Lead AI генерирует:
   * `02_SYSTEM_SPECS/[module].md` (сущности, инварианты, FSM, LaTeX-математика, схема баланса).
   * `configs/[module].yaml` (стартовые значения для игрового движка).
3. Файлы сохраняются в репозиторий. Project Owner при необходимости корректирует числа в `configs/[module].yaml` по своему усмотрению.

### ШАГ 3. Декомпозиция модуля в `03_ROADMAP/[module].md`
1. Project Owner отправляет **ПРОМПТ 3**.
2. Lead AI напрямую через GitHub изучает файловую структуру кодовой базы, проектирует план интеграции модуля и генерирует `03_ROADMAP/[module].md` со списком от 3 до 6 атомарных Issues (только заголовки Issues) с чекбоксами для каждого Issue.
3. **ТЗ на этом шаге НЕ пишется.** Шаг 3 фиксирует исключительно план работ.

### ШАГ 4. Исполнительный цикл 
1. **Генерация ТЗ:** Project Owner через **ПРОМПТ 4** запрашивает детальное ТЗ для первого открытого Issue из дорожной карты модуля. Lead AI изучает актуальный код на GitHub и выдает ТЗ на английском языке со строгим `ALLOWLIST`.
2. **Реализация:** Project Owner передает ТЗ IDE агенту. IDE создает на Github ветку `feature/[module]-issue-[N]`, пишет код и интеграционные тесты, пушит ветку и открывает Pull Request на GitHub.
3. **Аудит через GitHub:** Project Owner отправляет Claude **ПРОМПТ 5**, передавая только ссылку на PR или имя ветки. Claude напрямую изучает diff, код и тесты в репозитории:
   * **Если есть замечания:** Claude формулирует корректирующее ТЗ для Devin.
   * **Если задача принята:** Project Owner мерджит PR в `main`, обновляет чекбокс выполненной задачи в `03_ROADMAP/[module].md` и **запрашивает у Lead AI детальное ТЗ для следующего Issue**.
4. Цикл повторяется, пока все Issues модуля не будут закрыты.
5. **Финал модуля:** Project Owner повышает MINOR-версию проекта в `CHANGELOG.md` (`v0.X.0`), ставит релизный тег в Git, после чего чат по данному модулю считается завершенным. При необходимости последующей доработки модуля новые Issues добавляются вместе с чекбоксами к уже закрытым Issues в Roadmap-файле модуля.

```markdown

ПРОЕКТ: Goliath

<КОНЦЕПТ>

ШАГ 1: АРХИТЕКТУРНАЯ ОЦЕНКА МОДУЛЬНОСТИ
Проверьте концепт по 4 системным критериям:
1. Суверенность данных: Требует ли механика собственных уникальных таблиц/полей в базе данных?

ШАГ 2: ПРАВИЛА ФОРМАЛИЗАЦИИ ТЕКСТА
1. Пишите сухим, строгим, юридически выверенным языком геймдизайна. Никакой маркетинговой воды и художественных описаний.
2. КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать точные балансные числа. Используйте абстрактные системные термины: «базовая стоимость», «порог действия», «штрафной коэффициент».
3. Формулируйте механику строго по шаблону: Триггер -> Условие -> Механический эффект.
4. Опишите поведение в предельных и граничных ситуациях (нулевой остаток, превышение лимитов, одновременные события).
5. Четко зафиксируйте, какую картину видит игрок в интерфейсе и к чему приводит осознанное бездействие игрока.

ВЫХОДНЫЕ ДАННЫЕ:
- Архитектурное решение: [НОВЫЙ_МОДУЛЬ: module_slug | РАСШИРЕНИЕ_СУЩЕСТВУЮЩЕГО: module_slug]
- Целевой Библия-файл: 01_GAME_BIBLE/[module_slug].md
- Готовый Markdown-текст с метаданными в шапке (front-matter): `module`, `dependencies`, `in_scope`, `out_of_scope` и полным текстом Библия-файла.
```

### ПРОМПТ 3: Декомпозиция модуля в Roadmap (Шаг 3)
```markdown
ROLE: Ведущий инженер-программист и технический менеджер проекта (Lead Software Engineer & Technical Project Manager).
ПРОЕКТ: Goliath.
```
