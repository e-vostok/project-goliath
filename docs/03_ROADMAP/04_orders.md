# 03_ROADMAP / 04_orders

## Статус

Модуль 04_orders («Приказы»: подача приказов, распределение между игроками-судьями, вердикты, вкладка в Реестре, уведомления бота). **Модуль завершён 16.10.2026 (Issue 10): сквозной тест зелёный на SQLite и PostgreSQL, Spec приведён к факту (версия 1.2).**
Входы: Bible `docs/01_GAME_BIBLE/04_orders.md` (утверждена Project Owner 15.10.2026), Spec 1.2 `docs/02_SYSTEM_SPECS/04_orders.md` (1.1 — предел приказов на автора; 1.2 — приведение к факту), конфиг `configs/04_orders.yaml` и схема `backend/src/modules/_04_orders/config_schema.py`.
Зависимости: `00_core` (закрыт), `02_bot` (выпущен), `03_registry` (реализован, релиз отложен). `01_map` не требуется.
Релиз: MINOR; предложение — 0.7.0 вместе с Реестром, решение Project Owner после Issue 10.

Состояние на 15.10.2026: Bible, Spec 1.1, конфиг и схема готовы, кода нет. Решение Project Owner: не более 5 неразрешённых приказов на одного автора (`author.max_unresolved_orders`).

Работа делится на **одну исследовательскую задачу (ORD-0) и десять Issues**. Версии идут сквозной нумерацией проекта: каждый PR с видимым поведением поднимает PATCH на следующий за актуальным; релиз модуля — отдельная задача.

## Архитектурная цель

Владелец государства в штабе подаёт приказ: название, краткая суть, ссылка на статью ВК. Приказ немедленно получает номер и уходит на распределение: сервер выбирает судью с наименьшей загруженностью среди достижимых игроков, не равных автору, с рейтингом не ниже порога и числом ожидающих вердикта приказов ниже предела. Судья узнаёт о назначении из бота, открывает окно приказа, пишет вердикт. В Реестре на вкладке «Приказы» видны все приказы с тремя этапами и реальным временем; судья нигде не показывается. Если судьи не нашлось, приказ ждёт и фоновая задача повторяет попытку; если срок вышел, приказ получает отметку, но не переназначается.

Сервер гарантирует: приказ и вердикт неизменяемы; судья никогда не раскрывается игрокам; нагрузка судьи не превышает предел даже при одновременной подаче; сбой бота и ВК не ломает подачу и вердикт; сброс мира очищает приказы.

## Правила работы над модулем

- Постоянные правила Devin — `docs/devin_rules.md`; шаблон ТЗ — Промпт 4. ТЗ короткое, без таблиц, на английском.
- **Тесты:** по одному новому тесту на поведение, без матриц. Тестовая матрица Spec (Приложение T) — перечень допустимых поведений, а не обязательный набор: Lead в каждом ТЗ называет минимальный список для Issue.
- Класс слияния — в последней строке отчёта Devin: `ROUTINE` или `NEEDS LEAD AI REVIEW`. Новая миграция всегда требует моего ревью.
- Тесты с блокировкой и номерами выполняются и на SQLite, и на PostgreSQL (`DATABASE_URL_TEST`).
- Окна клиента не шире 910 px, без горизонтальной прокрутки; проверяется при каждом Issue с интерфейсом.

## Известные риски

1. **Доступ второго игрока к приложению.** Приложение «отключено», видят только администраторы. ORD-0 (F3) выяснил: доступ именным тестировщикам даётся в кабинете разработчика (роль «Администраторы» с правом «Тестирование» и/или «Тестовые группы»). Для приёмки судейской части нужен второй аккаунт с таким доступом; точные шаги будут в чек-листе Issue 6.
2. **Ссылка из бота не проверена на практике.** Передаёт ли ссылка нужный адрес внутрь приложения, неизвестно (ORD-0 проверит по документации, окончательно — только живая приёмка после Issue 6). Запасной путь описан в Spec: номер приказа в сообщении, поиск в Реестре.
3. **Предел приказов на автора занимает место при «молчащем» судье.** Решено: не более 5 приказов без вердикта на автора. Если назначенный судья не отвечает, место автора остаётся занятым до вердикта; при пяти таких приказах автор не сможет подать новый. Смягчение версии 1: администратор видит просроченные приказы в панели и может временно поднять предел в конфиге; переназначение судьи — в бэклоге.
4. **Игроки-призраки.** Любой, кто хоть раз открыл приложение, — игрок. Условие достижимости (по умолчанию включено) исключает не отвечающих без государства и без согласия, но владелец государства, перестав играть, остаётся судьёй; автопередачи нет. Администратор видит просроченные приказы в панели и решает вручную (например, правкой данных); переназначение вне версии 1.
5. **Расширение Реестра и бота затрагивает готовые модули.** Новые типы ячеек и обязательный ключ `requires_nation` во всех типах бота — изменения контрактов. Защита: существующие тесты остаются зелёными, `test_configs_validity.py` проверяет оба конфига до выкладки; конфиг бота и код выкладываются вместе.
6. **Квота Devin.** Десять Issues и один из них большой по объёму клиента. Порядок позволяет остановиться после Issue 5 с готовой подачей и таблицей; тесты — минимальные списки в каждом ТЗ.
7. **Блокировка PostgreSQL.** Корректность предела нагрузки при одновременной подаче проверяется только на PostgreSQL; обязателен прогон с `DATABASE_URL_TEST`.
8. **Время.** Все даты на экране — реальные, по московскому времени (`tick_timezone`); игровой календарь здесь не используется, что может сбивать игроков, видящих игровую дату в других окнах. Подписи окон должны быть однозначными.
