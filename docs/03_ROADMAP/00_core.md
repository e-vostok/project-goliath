# 03_ROADMAP / 00_core

## Архитектурная цель модуля

Заложить фундамент проекта: идентификация игрока через VK (без пароля),
доменные сущности `Player` / `Nation` / `Province`, универсальный примитив
«механический деятельный акт» (`ScheduledAction`), Tick DAG-оркестратор
с точкой расширения для будущих модулей-сателлитов, собственный игровой
календарь. По завершении модуля игрок может: открыть клиент, автоматически
зарегистрироваться, создать/отредактировать/удалить государство, и увидеть,
как срабатывает ход (даже без единого подключённого модуля-сателлита —
тик просто не находит зарегистрированных обработчиков фаз и сразу переходит
к `finalize_tick()`).

### Расширение v0.3.0 (часть 1): сведения о государстве

Государство получает описательные сведения: имя и должность лидера и обязательную ссылку на историю (статью ВКонтакте). Регистрация делится на два окна с переключением стрелками. Правила — Game Bible §2, §3, §8 и Spec 1.1 (Части 1–5). Новых таблиц и шагов Tick нет: три поля добавляются к `nations`, изменяются сразу, в расчётах Tick не участвуют. Остальные пункты v0.3.0 (население и уровень развития провинций, флаг и портрет) — отдельные следующие расширения, в эту часть не входят.

## Issues

- [x] **Issue 1: Data Layer & Config-Safe** — Модели SQLAlchemy (`Player`, `Nation`, `Province`, `ScheduledAction`, `GameClock`, `TickLog`) в `backend/src/modules/00_core/models.py`; Alembic-миграция начальной схемы; сид-скрипт таблицы `provinces` (временный плейсхолдер `id=1..100`, `nation_id=NULL` — см. открытый вопрос выше); `config_schema.py` (готов с Шага 2) подключён к загрузке при старте `main.py`; тест `test_configs_validity.py`. **Результат:** полный набор корневых таблиц ядра существует в БД, баланс валидируется до старта сервера, констрейнты `UNIQUE(owner_player_id)` / `UNIQUE(name)` / `UNIQUE(color_hex)` подтверждены тестом на реальной тестовой БД (INV-1, INV-2).

- [x] **Issue 2: Domain Simulation & Tick DAG** — `PlayerService` (get-or-create по `vk_user_id`); `NationService` (атомарные create/update/delete с проверкой уникальности и резервированием провинций, INV-3, INV-6); `ScheduledActionService` (постановка в очередь + алгоритм проверки частоты из Части 3 Спека); `TickOrchestrator` в `backend/src/core/tick/orchestrator.py` — генерик-раннер по перечислению `TickPhase`, точка регистрации обработчиков для будущих модулей, `finalize_tick()` (инкремент `current_turn`, пересчёт календаря, запись `tick_log` вне основной транзакции — INV-TICK-ATOMICITY). **Результат:** доменная логика государства и очереди действий работает и покрыта тестами на реальной БД без моков; тик-движок проходит полный цикл (даже без единого зарегистрированного модуля-фазы) и корректно откатывается при симулированном исключении в обработчике.

- [x] **Issue 3: API & DTO** — Роуты `POST /api/v1/auth/vk`, `GET /api/v1/players/me`, `GET/POST/PATCH/DELETE /api/v1/nations`, `GET /api/v1/provinces`, `GET /api/v1/game-clock`; DTO-схемы из Части 5 Спека; Bearer-JWT авторизационный dependency; маппинг доменных ошибок на `ErrorResponse.code` (`NAME_TAKEN`, `PROVINCE_TAKEN` и т.д.). **Результат:** полный REST-контракт ядра доступен и покрыт интеграционными тестами через `httpx.AsyncClient` против реальной тестовой БД, включая проверку кодов ошибок на каждое граничное состояние из Спека.

- [x] **Issue 4: Client UI / VKUI** — Auth-gate (`ScreenSpinner` на время резолва `/auth/vk`) в `AppShell`; `PanelCreateNation`, `PanelNationHome`, `ModalConfirmDeleteNation` в `frontend/src/modules/00_core/components/`; хуки вызова API (`useAuth`, `useNation`, `useProvinces`) с обработкой состояний загрузки/ошибок и инлайн-маппингом `ErrorResponse.code` на конкретный `FormItem`; вызовы `@vkontakte/vk-bridge` (`VKWebAppInit`, `VKWebAppTapticImpactOccurred`); базовый API-клиент в `frontend/src/shared/`. **Результат:** игрок может пройти полный цикл создания/просмотра/редактирования/удаления государства через интерфейс VKUI на десктопе, с корректной обработкой всех серверных ошибок и тактильным откликом.

- [x] **Issue 5: Integration / E2E** — Сквозной тест без моков (Anti-Mock Guard): регистрация игрока → создание государства через реальный API-вызов → запись в БД → прогон полного цикла тика через `TickOrchestrator` → верификация итогового состояния (`current_turn` увеличен, `tick_log.status = COMPLETED`); отдельный сценарий отказа (исключение в фазе → откат, `current_turn` не изменился, `scheduled_actions` остались `PENDING`); интеграционный тест `PanelCreateNation` (React Testing Library) на реальный вызов API-клиента и корректный рендер серверных ошибок. **Результат:** подтверждена сквозная целостность модуля от клика в интерфейсе до записи в БД и обратно, без единого мока состояния.

- [x] **Issue 6: Automatic Tick Scheduling** — `scheduler.py` в `backend/src/core/tick/` (`seconds_until()`, `run_scheduled_tick()`, `scheduler_loop()` — свежая сессия на каждую итерацию, catch-up ровно один раз при просроченном `next_tick_at`); `register_tick_handlers()` подключён в `lifespan` до старта планировщика; `tick.retry_delay_seconds` в конфиге — пауза перед повторной попыткой после сбоя (никакого горячего цикла); `tick_log.turn_number` переведён с `UNIQUE` на обычный индекс — полная история попыток по каждому ходу (миграция 0002, заодно починен `tick_log.id`: в 0001 не было ни PK, ни последовательности); миграция 0003 добавляет пропущенные внешние ключи и приводит UNIQUE-индексы к объявленному в моделях виду; тест-страж `test_model_migration_drift.py` ломает сборку при будущем расхождении моделей и миграций. **Результат:** цикл хода работает на живом сервере сам, без ручного запуска и независимо от присутствия игроков (Bible §4); один сбойный тик не останавливает последующие, все попытки остаются в `tick_log`.

### Расширение v0.3.0 (часть 1): Issues 7–9

- [ ] **Issue 7: Профиль государства — данные, конфиг, сервис и API** — Три nullable-колонки `leader_name`, `leader_title`, `history_url` в `nations` (`models.py`) и одна новая миграция (следующая после текущей head; через `batch_alter_table`, upgrade/downgrade чисто на SQLite и на реальном PostgreSQL); применение `configs/00_core.yaml` и `config_schema.py` из Spec 1.1 одним PR с обновлением `test_configs_validity.py` (базовый конфиг выносится в одну общую функцию, чтобы следующие расширения не требовали правки каждого теста) и тестом «верхние границы `le` не больше длин колонок»; три новых доменных ошибки (`LEADER_NAME_INVALID`, `LEADER_TITLE_INVALID`, `HISTORY_URL_INVALID`) и их статусы в таблице соответствия `main.py`; `service.py`: нормализация и проверки Части 3 Spec (длины, символы `Cc`/`Cf`, ссылка: `https`, домен из конфига, путь `/@название`, без порта, логина, параметров и фрагмента), порядок проверок при создании, правила PATCH (`null` = не менять, пустое значение = ошибка), старые государства с NULL-полями; DTO и роутер: три поля в `NationCreateRequest`/`NationUpdateRequest`/`NationDTO`, новый `GET /api/v1/nations/rules` (`NationRulesDTO`); фабрики и тесты на реальной БД без моков; защитный тест расхождений моделей и миграций остаётся зелёным. **Результат:** сервер принимает, проверяет, хранит и отдаёт сведения о государстве по Spec 1.1; старые государства продолжают работать; весь набор тестов зелёный, миграция проверена на PostgreSQL.

- [ ] **Issue 8: Регистрация в два окна и профиль в интерфейсе** — `types.ts` и `api-client.ts` (три поля в DTO, `NationRulesDTO`, новые коды ошибок, метод `getNationRules`); хук для лимитов с сервера (числа в клиенте больше не дублируются); `PanelCreateNation` как контейнер из двух окон со стрелками «назад»/«вперёд» и текстом «Шаг N из 2» (окно 1 — название, цвет, провинции, имя и должность лидера; окно 2 — ссылка на историю), данные сохраняются при переключении, кнопка подтверждения в обоих окнах активна только при заполненных обязательных полях, отправляется один запрос; ошибки по полям (`LEADER_NAME_INVALID`, `LEADER_TITLE_INVALID`, `HISTORY_URL_INVALID` и прежние), индикатор ошибки у окна, к которому поле не относится; `PanelNationHome`: имя и должность лидера, кликабельная ссылка (`target="_blank" rel="noopener noreferrer"`), «не указано» у старых государств, редактирование одной формой с отправкой только изменённых полей; раскладка рассчитана на ширину до 1000 px; тесты на msw с реальными кодами ошибок Spec. **Результат:** игрок проходит регистрацию в два окна и редактирует сведения государства; ошибки сервера показываются у нужного поля и окна; фронтенд собирается без ошибок типов.

- [ ] **Issue 9: Интеграция и E2E на реальном PostgreSQL** — сквозной тест без моков: вход через VK → `GET /nations/rules` → создание государства со сведениями → проверка строки в БД напрямую → `PATCH` сведений → повторное чтение → удаление; отдельные сценарии: старое государство с NULL-полями (чтение отдаёт `null`, смена названия проходит без заполнения профиля, заполнение профиля по частям переводит его в полное состояние), отказ при пустой или недопустимой ссылке с кодом по полю; новые тесты и защитный тест расхождений запускаются в том числе на реальном PostgreSQL через `DATABASE_URL_TEST` (отдельная метка, пропуск при отсутствии переменной); админ-сброс мира удаляет государство вместе со сведениями. Весь существующий набор на PostgreSQL остаётся пунктом бэклога. **Результат:** подтверждена сквозная целостность расширения от формы до записи в БД на боевой СУБД, а не только на SQLite.
